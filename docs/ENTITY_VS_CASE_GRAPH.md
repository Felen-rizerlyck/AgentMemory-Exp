# 建边方式的可扩展性分析：案例-案例 边 vs 实体-关系 图

> 起因：对 `GRAPH_DECISION.md` 方案 B（案例关系图）的建边机制提出可扩展性质疑——每新增案例都要对全库扫描一遍，担心效率与出错率随规模恶化；并提出替代设想：**以"单步操作"为实体、操作间的时序/逻辑关系为边**，通过共性实体规范化让攻击链之间自然连通。
> 状态：**分析稿，非决策**。你未确定，本文只把两种模型的权衡讲清楚，最后列出需要你拍板的决策点。
> 关联：`GRAPH_DECISION.md`（方案 B 的建边三步）· `PENDING.md` §1（"IOC/技术独立成实体属另一议题"——本文即展开该议题）· `RELATION_TIER_CRITERIA.md`（案例级边判据，本文不推翻它，见 §5）。

## 一、你的担忧是否成立：先确认问题

**成立，但需要精确定位是"哪一步"在恶化。**

方案 B 的建边（GRAPH_DECISION §2.4）分三步：机械候选 → 模型初判 → 人工确认。真正随规模恶化的有两处：

| 步骤 | 复杂度 | 规模效应（有实测） |
|---|---|---|
| ① 机械候选：新案例与**全库 N 个案例**逐一比较（R 系规则） | **O(N) / 新案例** | R6 覆盖率 ~56%（130/231 对），即每案例约 0.56N 条候选 |
| ② 人工确认候选 | **O(候选数)** ≈ 0.56N | 候选精度 ~19%（25/130）→ 确认量线性涨，且 80% 是噪声 |
| ③ 全库边维护空间 | **O(N²)** | — |

实测佐证：案例 9→22 时，评测噪声/查询 0.25→0.91（`findings_round2.md`）——这是"案例级两两比较"的规模代价第一次被量化抓到。

所以你说的两点都对：
1. **效率**：每新案例的候选生成与确认成本随 N **线性**增长（N=22 时 ~12 条候选/案例，N=100 时 ~56 条），全库两两关系 O(N²)。
2. **出错几率**：候选精度 ~20%，人工在噪声里挑边，规模越大越容易漏判/误判。

**但要注意**：当前方案不是"每次遍历所有实体条目"，而是"遍历所有案例"——遍历对象是案例（22 个），不是实体。你直觉里担心的"实体条目"其实已经指向了你提议的模型：**把遍历对象从"案例"下沉到"实体"后，成本结构才真正改变**。这一点正是下面 §3 的核心。

## 二、你提议的模型：精确复述

- **节点 = 规范化后的"单步操作"实体**，例如：
  - 动作实体：`whoami`、`cat /etc/shadow`、`nslookup $<sub>.<domain>`
  - 工具模板实体：`wmic /node:{ip} process call create {cmd}`、`ssh -i {key} -o StrictHostKeyChecking=no {user}@{ip} "{cmd}"`
  - 目标/基础设施实体：`{ip}`、`{domain}`（可选，或留在案例 IOC 层）
- **边 = 步骤间的时序关系**（谁先谁后，来自日志时间戳）**或逻辑关系**（发现→持久化，来自 kill-chain 阶段）
- **跨案例关联 = 隐式**：两个案例共享同一规范化实体，就在图上自然相邻，**无需显式建"案例-案例"边**。

关键洞察：这个模型里**没有"案例关系"这个概念了**——你不需要回答"这条完整攻击链和那条完整攻击链相似吗"这种全局判断，只需要判断"这一步操作是不是我见过的实体"。判断对象从"整条链"缩小到"单步操作"，这正是可扩展性和低出错率的来源。

## 三、复杂度与出错模式对比

| 维度 | 案例-案例（方案 B） | 实体-关系（你的提议） |
|---|---|---|
| 新增案例成本 | O(N) 两两比较 + 人工确认 ~0.56N 候选 | O(k)，k = 该案例步骤数（有界，通常 2–8），与 N **无关** |
| 全库维护 | O(N²) 边空间 | O(总实体数) + 案例内局部边 |
| 实体/案例去重 | 无显式去重，靠人工"合并强化"判断 | 规范化实体**哈希查找 O(1)/O(log M)**，确定性合并 |
| 出错主因 | 模糊的"链级相似"人工判断 | 实体规范化不当（同义异形漏合并 / 异义同形误合并） |
| 出错可检测性 | 低（边是主观裁定，难自动核对） | 高（实体重复=确定性；规范化规则可单测、可回归） |

**一句话**：你把"每次新增案例都要做的、无界的 O(N) 后置比较"，换成了"每次提取案例时做的、有界的 O(k) 前置规范化"。成本总量没消失，但**从无界变成了有界，从后置分摊变成了前置一次性**，且出错点从"主观判断"变成了"可自动核对的规则"。这是真实且有利的 trade-off。

## 四、实体规范化的真实难点（不夸大，这些是要付的账）

你的设想正确，但"共性实体提取与规范化"不是免费的，有四个坑必须正面处理：

### 4.1 粒度边界（最难的决策）
`wmic /node:10.20.6.179 process call create "cmd.exe /c whoami"` 拆成几个实体？

- **太粗**（整条命令 = 1 实体）：IP 一换就是新实体，退化成案例级，失去聚合。
- **太细**（工具 / 动作 / 目标各一实体）：实体爆炸，规范化规则数量激增。
- 建议原则：**以"可复用的行为骨架"为粒度**——工具模板是一个实体（参数化掉 IP/目标），动作（whoami/读文件）是一个实体，两者以边相连。这与 MITRE 的"技术"粒度对齐（T1047 是技术实体，其"参数"是实例变量）。

### 4.2 参数化（规范化的核心动作）
`wmic /node:10.20.6.179` 与 `wmic /node:10.20.4.70` 必须归并成 `wmic /node:{ip}`。这就是"规范化"。
**好消息：项目里已有同构物**——`pattern_probes` 结构正则（如 DGA `\b[0-9a-f]{8}\.[a-z0-9-]+\.(net|com|org)\b`、WMIC `wmic\s+/node:`）正是"实体的正则投影"，只是它现在用于**检索探测**而非**存储聚合**。把它从"检索通道"升级为"实体规范化规则"，是现成的路，不用从零设计。

### 4.3 同义异形归一
`cmd.exe /c whoami` vs `cmd /c whoami` vs `whoami`；`net user /add backdoor ...`（截断）vs 完整命令——需要归一化规则（去扩展名、去截断、命令别名映射）。这是持续维护成本，但可沉淀成一张规则表 + 单测。

### 4.4 时序边 vs 逻辑边（要分清）
- **时序边**（谁先谁后）：来自日志时间戳，**易得但噪声大**（并发、日志乱序、跨源时钟漂移）。
- **逻辑边**（whoami=发现 → net user /add=持久化）：来自 kill-chain 阶段标注，**更有价值但需人工**。
- 建议：时序边机器生成、标"观察级"；逻辑边走 kill_chain 阶段（案例里**已有**这个字段，见下 §5）。

## 五、与当前验证项目的张力（诚实）

### 5.1 不是推翻，而是"把已有字段升级为实体"
你的提议**没有破坏**现有案例结构，反而把它显式化：

- 每个案例里**已经有** `kill_chain`（阶段序列，如"发现(whoami) → 持久化(创建后门账户)"）——这就是"步骤序列"的雏形，只是步骤还是**文本**，没提成**实体**。
- `pattern_probes` 已经是"规范化实体的正则投影"。
- 你的提议 = 把 `kill_chain` 的步骤从"字段文本"升级为"独立实体节点"，把 `pattern_probes` 从"检索辅助"升级为"存储聚合规则"。

**这大幅降低了迁移成本的心理门槛**：不是另起炉灶，是给现有结构"去扁平化"。

### 5.2 但有两处真冲突，必须明说

1. **"案例"不能消失，只能降格为"视图"**。检索最终呈现给分析者的仍是"一条完整攻击链"（有序实体序列 + 案例元信息），否则会丢掉对分析最有价值的**攻击链完整性**。实体-关系图只负责**底层存储与跨案例聚合**，案例层负责**上下文与呈现**——两层都要，不能只存实体和边。
   - 建模上这等价于"案例 = 有序实体序列（超边）"，而非"案例 = 一个节点"。

2. **评测框架要重写**。当前 `eval/` 的 gold 是"案例对"（231 对）、指标是"扩展新增 helpful/噪声"。实体-关系下，gold 变成"实体共享"（确定性、可自动核对），大部分评测**可以自动化**——这是净收益，但是一次性的迁移成本。`RELATION_TIER_CRITERIA.md` 的案例级边判据在实体模型下**不再需要**（因为不需要人工裁定"这两案例 helpful 吗"），它的作用退化为"验证实体聚合是否合理的抽样手段"。

## 六、我的判断与演进路径（供你拍板）

**结论：你的方向在可扩展性和出错率上优于方案 B 的"案例对案例"建边，且与现有项目结构兼容度高于直觉印象（§5.1）。但它是一次"存储层重构"，不是方案 B 的小补丁，不该在 22 案例的现阶段仓促切换。**

建议分三层演进，而非二选一：

| 阶段 | 动作 | 触发条件 | 代价 |
|---|---|---|---|
| **短期（现在）** | 把 `pattern_probes` + `kill_chain` 逐步**实体化**：每案例提取时产出"规范化步骤实体列表"（作为案例的一个新字段），**先不建图**，只积累实体词典 + 归并规则 | 下一批日志起即可，零架构改动 | 每次提取多写一个字段（O(k)） |
| **中期** | 实体词典够大后，把"实体共享"做成检索**第二通道**：实体命中 → 定位案例 → 展示。与现有符号双通道并列 | 实体数 ~50–100 | src/retrieve.py 加一条实体索引 |
| **长期** | 若规模确实 >50 案例、案例级建边 O(N) 开始疼，**再**把实体-关系升为主存储形态，案例降格为"有序实体序列视图" | 规模实测触发（FRAMEWORK_READINESS 的重估点） | 重写评测 gold、迁移 memory_store 结构 |

这样做的逻辑：**实体规范化是"提取时"就该做的事，无论最终用不用图，它都让案例更结构化、更可检索**——所以短期动作是纯收益、零风险；而"要不要把图当主存储"这个重决策，可以等到规模证据真正出现再定，不被现在的 22 案例规模逼着提前下注。
