# 动作序列索引 + 逐位淘汰匹配：可行性评估与截断问题

> 承接实体模型系列。你的三项决策已记录：① 粒度 = 按动作划分（去除 IP 等变量后的指令，即工具模板）；② 实体提取暂缓；③ 保留完整案例、以动作为索引。
> 本文评估你提出的检索方案：案例索引为动作序列（Act1→Act2→Act3→Act4），图检索的同时逐位匹配、淘汰不符项、返回匹配项 + 相似项。
> 状态：分析稿。只谈机制，不动任何已有文件。

---

## 一、你的方案本质：前缀树（Trie）+ 反向索引

把每个案例的动作序列建成一棵 Trie（前缀树），当前攻击的动作序列就是一条"查询路径"，沿树逐位走、逐位剪枝：

```
        Act1
       /    \
     Act2   Act5        ← Act1 命中两条链：一条走 Act2、一条走 Act5
     /        \
   Act3       ...       ← 实际是 Act2 → Act5 分支淘汰（你说的"后者因不符而淘汰"）
   /
 Act4
```

- **反向索引**：Act → 包含它的案例集合（"通过 Act1 找到候选"）。
- **Trie 前缀匹配**：从命中动作起，沿案例序列向前比对。
- **逐位淘汰**：比对中不吻合的分支剪掉。

**可行性：可行，且是标准结构。** 这是字符串/序列检索里最成熟的方案（Trie、有限状态机），查询复杂度 O(k)，k = 观察到的动作数，与案例库规模无关——正好回应了你最初"遍历全库效率低"的担忧。而且"边观察边匹配"是**流式**的：拿到一个动作走一步、剪一次枝，能实时回答"当前最像哪条链、进行到第几步"。

---

## 二、你担心的截断问题：不是"检索不到"，是"前缀遮蔽"

你的例子：案例 A = Act1→Act2→Act3→Act4，案例 B = Act1→Act2→Act3。观察到 Act1→Act2→Act3 时，B 是 A 的**前缀**（B 的每个动作都在 A 里、顺序一致、A 只是更长）。

**诊断**：问题不出在结构，出在停止条件"匹配到最短重合就停"——走到 Act3 时 B 已经完整（3 步），于是停、返回 B，A（还有第 4 步未观察）被遮蔽。

所以你的担心**在你的停止规则下成立**，但根因是停止策略，不是序列索引这个结构本身。

---

## 三、修正：停止条件从"最短重合"改为"最长可观察重合"

正确行为：**沿当前观察到的动作，在 Trie 里走到最深的位置，返回路径上所有案例 + 标注匹配深度**，而非停在第一个完整匹配的案例。

观察到 Act1→Act2→Act3 时，返回两个：

| 案例 | 匹配深度标注 | 呈现含义 |
|---|---|---|
| B = Act1→Act2→Act3 | 完整匹配（3/3） | 当前行为与 B 完全一致 |
| A = Act1→Act2→Act3→Act4 | 前缀匹配（3/4） | 已重合 A 的前 3 步，**第 4 步（Act4）待观察** |

这样 A 不被遮蔽，而且 A 的"未观察到的 Act4"恰好变成**预测**——"当前攻击已命中 A 的 3/4，下一步可能 Act4"。这正是实体模型相对案例级检索独有的预测能力。

**"返回匹配项 + 额外一两个相似项"的设想也因此自然成立**：在 Trie 里，相似项 = 匹配路径上每个分叉点被剪掉的分支（如 Act1 处的 Act5 分支）——它们与匹配项共享最长前缀，是最"接近"的备选，天然就是你要的相似项，不需要额外设计。

---

## 四、更深的点：前缀 vs 分叉，必须在入库时区分

你的例子还暴露了一个建模问题：**一个案例是另一个案例的前缀时，该合并还是共存？** 这不能留给检索时纠结，必须在入库时定死：

| 情形 | 定义 | 处理 |
|---|---|---|
| **前缀** | B 的每个动作都在 A 里且顺序一致，A 只是更长（同工具链，这次没走到 Act4） | **合并**：B 是 A 的一次"不完整观测"，记入 A 的观测条目（"某次仅见 3 步，无后续证据"） |
| **分叉** | Act3 之后 A 走 Act4、B 走 Act5，两条链 | **共存**：Trie 在 Act3 处分支，两案例独立 |

区分标准（与现有提取准则一致）：**同工具链 + 动作序列是包含关系 → 合并（不完整观测）；后续动作不同 → 分叉（独立案例）**。这就是 `EXTRACTION_CRITERIA.md`"高度相似→合并强化"在动作序列形态下的具体化。

入库时做对区分，检索时就只剩"分叉分支"的排序，不再有"前缀遮蔽"的歧义。

## 五、你方案的边界条件（诚实标注，两点）

1. **严格顺序假设**：`→` 表示严格先后。当前合成数据的链是严格顺序的，假设成立；但真实攻击中侦察/发现动作可能交错、某步可跳过。若未来遇到"顺序可变"的链，前缀匹配不够用，需升级为**子序列/序列对齐匹配**——这是后话，当前规模不用预支。

2. **头部匹配假设**：前缀匹配假设日志从 Act1 开始观察。若某条日志只见 Act3→Act4（前段在别的源/别的批次），前缀 Trie 会 miss。这对应上一份文档的"命中链中段"问题，解法是**反向索引兜底**（任意动作 → 案例 + 位置，不要求从头开始）。你方案里的"图检索找候选"已经是这个反向索引的雏形，只需把它做成"任意动作可查 + 带位置"，而非仅"首动作可查"。

---

## 六、结论

1. **方案可行**，核心结构（反向索引 + Trie 前缀匹配 + 逐位淘汰）正确、高效、流式，且"相似项 = 剪掉的分叉分支"天然成立。
2. **截断问题可解**：停止条件从"最短重合"改为"最长可观察重合 + 返回路径上所有案例 + 标注匹配深度"，A 不被 B 遮蔽，还白得一个预测能力。
3. **一处入库约定**：前缀案例（同链不完整观测）合并、分叉案例（后续不同）共存，检索前就消除歧义。
4. **两处边界**：严格顺序假设、头部匹配假设——当前数据成立，未来真实数据时分别升级为子序列匹配和"任意动作带位置"的反向索引。
