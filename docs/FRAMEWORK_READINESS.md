# 框架选型就绪度评估（记忆模块 v1）

> 问题：现有结果是否足以确定后续**实际应用**时的记忆模块框架选型？
> 结论：**主框架可以条件锁定（v1），但有两个补充测试值得先做**——其中「评分修复对照测试」与将锁定的框架形态强耦合（阻塞性）；「查询形态测试」是唯一可能改变框架结论的补充测试。其余问题是"等数据"而非"加测试"。

## 一、逐项就绪度矩阵

| 决策项 | 当前证据 | 就绪度 | 条件 |
|---|---|---|---|
| ① 存储形态：规范化案例 JSON 库 + 关系表（零图库/零向量库） | 全部评测与审计的运行基础；成本/可审计性对比 | **可条件锁定** | 规模 >50 案例 或 真实数据接入时重估 |
| ② 召回机制：符号双通道为主（keys/mitre/ind/sig/probes） | 前瞻测试 KNOWN 21/21 强档；相对比较（probes 贡献=档位/排序稳定） | **可条件锁定** | 查询形态变化时重估（见补测 3） |

## 二、为什么"现在条件锁定"是可接受的

1. **框架 vs 参数的分野**：前瞻测试暴露的 token 重复计分是**打分器内部参数问题**，与架构选择正交——它不动摇①②③，只影响④之前的校准。
2. **决策颗粒度匹配**：本轮决策对象是"验证项目内的流程与结构设计"，证据等级 = "设计约束级"（协议 §8 已定义）；无限补测的边际信息递减，且部分问题本质上要**等真实数据**（前瞻批次天然回答）。
3. **条件锁定 + 重访触发** 是比"无限测试"或"裸锁定"都更稳的中间态。

## 三、建议补充测试（按性价比排序，注明"能改变什么"）

### 补测 1：评分修复对照测试（阻塞性，建议先做）
- 做法：把候选修法（至少 #4 跨通道去重，可带 #1/#2/#3）实现为**离线评分变体**（不动 src/retrieve.py 主流程），全量重跑四套评测（C0–C5 / 全量召回 / 前瞻 / 负样本）出 before/after 对照表。
- 能改变：兑现"修复后基线"的数字；验证修复不伤已知召回（尤其 005/006 等高变体案例）；给④定校准前提。
- 前置：你裁定修法（或先授权模拟）。

### 补测 2：精度压力测试（近邻负样本 + 良性含词流量）
- 做法：机械化构造 20–40 条——(a) 同产品族不同漏洞（如另一种 Java 反序列化变体 vs 006）；(b) **含 `select`/`base64`/`process` 等词但完全良性的业务行**（SQL 查询日志、CDN base64 URL、栈追踪）。
- 能改变：量化修复**前后**的残余误报率；若修复后仍高 → 框架需增设"强档人工确认层"（③ 的一个新附条）。

### 补测 3：查询形态测试（唯一可能改变框架结论的补测）
- 做法：构造 10–20 条**自然语言/模糊查询**（"之前那个 SSH 横向移动的案例"、"找 DGA 相关的"），测召回。B-nl 组已知偏乐观（attack_type 直接含键）。
- 能改变：若 NL 查询显著掉分 → 需要在框架中加**向量 advisory 通道**（C6/C7 预留位）——这是④从"未定"变"必要"的唯一证据路径。

### 补测 4：规模/维护性观测（不是一次性测试）
- 每批新数据先跑前瞻测试即天然测点；到 ~40–50 案例时重估：噪声/查询、推导候选量、keys/probes 维护负担。

### 补测 5：下游效用 A/B（决策后验收用）
- 图采用后选 2–3 批次回放，对比"有/无扩展输出"的分析结论质量（定性）。

## 四、建议决策路径

1. **现在**：GRAPH_DECISION §6 填「条件采纳 B（现形态）」+ 本文件作为 v1 条件锁定的附件（重访触发：查询形态变化 / 规模 >50 / 真实流量接入 / 修复后指标异常）。
2. **随即**：补测 1（修复对照）→ 裁定修法 → 回归；**然后**补测 2/3（半天量级）。
3. **并行**：gold 38 条复核（影响边细节，不影响主结论）。
4. **持续**：每批前瞻测试 + 规模观测；真实数据试点时按重访触发重估。
