# 决策简报：是否采用"图"（案例关系扩展）

> 本文只解决**采不采**的问题；关系细则（边判定、推导规则、裁定等）见 `PENDING.md` §1，后议。
> 术语口径：本项目的"图" = **案例关系图** —— 节点 = 案例（CASE-xxx），边 = 案例间关系（`eval/relations_gold.json` 的 36 对矩阵即边集）。现阶段不包含图数据库、不包含向量检索。

---

## 1. 三个选项

| 选项 | 内容 | 增量成本 |
|---|---|---|
| **A 不采用** | 维持现状：检索只返回命中案例；关联案例靠分析时人工翻库 | 0 |
| **B 轻量关系层**（建议评估） | 案例间显式边 + 检索后一跳扩展 + 输出以"关联参考"标注；边 = 机械候选 + 人工确认（零图库/零向量） | 一次性小改 src/retrieve.py；每新案例几分钟确认 |
| C 图数据库 + 向量堆栈 | GraphRAG / 向量库 / LLM 抽取实体关系 | 高，前轮已论证现阶段不划算 |

## 2. 证据汇总

### 2.1 首轮评测（`eval/results/report.md`，gold 直连 = 上界口径）

- **预注册判据全部达成**：新发现:噪声 — C3 33:5 / C4 20:4 / C5 21:3（均 ≥2:1）；误导 0；负样本零扩展 0/9。
- 基线字面通道只捞回 46 个 helpful 槽位中的 **13 个** → "关联案例展示"的增量空间真实存在。
- 代价：候选数 1.5→2.3 条/查询（分析者负担可控）。
- 噪声 5 条中 4 条可归因于已知缺陷"通用词泄漏"的假种子（在 `PENDING.md` §2，修复后改善）。
- 缺口：跨簇 chain_sibling 边未裁定 → **跨簇扩展的价值尚未检验**（只影响上限，不改变总体倾向）。

### 2.1b 第二轮评测（扩图后：95 查询 / 22 案例 / 231 对）

- 判据分化：**C4（跨簇/阶段类稀疏边）唯一通过**（26:10，2.6:1）；C3 110:68、C5 92:62 未达标——稠密簇内边 + 多种子联合扩展在大规模下噪声放大（首轮"簇内不冗余"的乐观读数属样本不足）。
- 噪声机制定位：单种子查询噪声 0.00 / 多种子 2.52；**仅从 top-1（或 must）种子扩展 → 三配置全部 110/0、26/0、92/0**（口径注意：helpful 按 must 邻域定义，属 gold 直连上界的一部分）。
- 本轮发现并修复一个自身缺陷：CASE-013 裸探针 `getRuntime().exec` 过泛 → 负样本强分误命中；修订后负样本零扩展恢复 0/9。
- 结论：扩展价值随规模放大（新发现 33→110），但**必须同时采纳"稀疏边集（C4 类）+ top-1 来源策略"**；跨簇 chain_sibling 仍待裁定。

### 2.2 边能否自动生成？（机械推导实测，231 对全量）

| 规则 | 推导边数 | 覆盖 helpful | 精度 |
|---|---|---|---|
| R0: mitre∩≥1 | 113 | 21/25 | 19% |
| R1: 后段阶段∩≥1 | 11 | 4/25 | 36% |
| R2: R0∪R1 | 122 | 24/25 | 20% |
| R5: 结构化令牌∩ | 63 | 10/25 | 16% |
| R6: R2∪R5 | 130 | **25/25** | 19% |

结论：**全覆盖可达（R6 25/25），但精度约 20%** → 单条规则要么漏要么脏，"**候选生成 + 人工确认**"仍是唯一可行路径（130 候选 → 人工裁出 25 helpful）；纯自动不值得。采纳 B 不需要养任何重型设施，边际维护成本与你们现有"手写案例"的节奏同量级。

### 2.3 成本对比

| | A | B | C |
|---|---|---|---|
| 一次性 | 0 | src/retrieve.py 加 `--expand`（默认关）+ 关系存储 | 搭建向量库/图库/抽取管线 |
| 持续 | 0 | 每新案例数条边确认；回归跑评测 | 索引重建、模型漂移管理、抽取质量监控 |
| 风险 | 漏关联 | 扩展噪声（已有门控+标注缓解） | 成本高 + 新失败源 + 非确定性 |

### 2.4 方案 B 的图如何构建 · src/retrieve.py 的职责（决定前确认）

**节点与边**：节点 = 案例（CASE-xxx，即 `data/memory_store.json` 的条目本身）；边 = 案例间关系记录 `{a, b, types, evidence, confirmed}`。本方案不引入"实体级"节点（IOC/技术独立成点属另一议题，见 PENDING §1）。

**边放在哪**：`data/memory_store.json` 新增顶层 `relations` 数组（与 `cases` 平级：单一事实源、可 diff、可审计）。`eval/relations_gold.json` 是评审工作版，定案后并入 `relations`。

**边怎么产生（三步，无黑盒）**：
1. **机械候选**（纯字段规则，非模型判断）：每批提取新案例后，用 R 系规则（mitre∩ / 后段阶段∩ / 结构化令牌∩）对全库扫描 → 每新案例得数条候选（全库实测：130 候选 → 25 helpful）。
2. **初判 + 证据**：模型（Agent）对候选给出建议 tier / 关系类型 / 证据引文（必须引用日志可见的具体 token），不臆造、不猜测。
3. **人工确认**：你复核 accept/调整，写 `confirmed: true` 才生效、才可能出现在检索输出里。
   → **模型不自行"决定"关系；模型只做"筛候选 + 带证据初判"，确认闸门在你。**

**src/retrieve.py 的职责（两项，均不改现有打分）**：
- ① **入口检索：完全不变**（C0→C2 评分逻辑一行不动）。
- ② **扩展输出**（`--expand`，默认关；采纳后启用）：对 **top-1 且 ≥门槛** 的种子案例，查 `relations` 中已确认的 helpful 边，打印"关联参考"块——1 跳、不做二次排序、不并入命中列表、明确标注"非命中"。负样本 / 无达标种子 → 零输出。
- 候选生成与自查建议放独立小工具（拟 `relations.py`），保持 src/retrieve.py 单一职责。

**输出真实模拟（用当前数据实跑，非示意）**：

```
== 查询: /api/v1/ping?cmd=127.0.0.1;id handle=com.tangosol.coherence.mvel2.sh.ShellSession&cmd=id
   [CASE-010] score=30(强) Web 应用命令执行：WebLogic ShellSession（MVEL 句柄）
        - keys×3: cmd=127.0.0.1;id,com.tangosol.coherence.mvel2,shellsession
        - probe×4: com\.tangosol\.coherence
        ↳ 关联参考（非命中；仅已确认边，1 跳）:
           · CASE-006 [same_technique/shares_payload] 共享 `cmd=id` 命令探针
           · CASE-011 [same_technique/shares_payload] 共享探针模板 `cmd=127.0.0.1;id`
           · CASE-013 [same_technique/same_family] Java 表达式引擎类（MVEL / SpEL）
           · CASE-016 [same_technique/shares_payload] 共享 `cmd=id` 探针
           · CASE-022 [same_technique/shares_payload] 共享 `cmd=id` 探针

== 查询（负样本）: PUT /upload/file.jsp <%Runtime.getRuntime().exec(...)%>
   [CASE-006] score=3(弱) …（未达强档门槛）
        ↳ 不输出关联参考（种子未达标；负样本路径零输出）
```

**不做的事**：不自动建边、不做嵌入/向量相似度、不做多跳扩散、不把关联案例当"命中"并入结论证据链——"关联参考"只是给分析者的上下文候选，引用与否由分析显式决定（与"独立事件"准则兼容）。

## 3. 建议：条件采纳 B

采纳条件（同时满足才落地）：

1. **gold 复核后预注册判据仍成立**（若 helpful 边在复核中大幅缩水 → 重估）；
2. 扩展输出以"**关联参考（经 XX 关联）**"呈现，**不进入结论证据链**、不改变"日志按独立事件处理"准则 —— 与现有审计纪律兼容；
3. 边一律"机械候选 + 人工确认"，不自动新增；
4. `PENDING.md` 的修复项（通用词泄漏等）不阻塞本次决策，但**上生产前一并处理并回归**；
5. **扩展来源策略固定为 top-1 种子（或 must-only）**——第二轮评测显示全种子联合是噪声唯一来源（110/0 vs 110/68）；边集优先稀疏跨簇/阶段类（C4 类），稠密簇内边默认不启用。

## 4. 落地清单（若采纳）

1. `data/memory_store.json` 增 `relations` 字段（或独立 `relations.json`）：`{a, b, types, evidence, confirmed: true}`；
2. `src/retrieve.py` 加 `--expand`（默认关）：种子（≥门槛）→ 列一跳邻居 + 关联理由；负样本路径零触发；
3. `EXTRACTION_CRITERIA.md` 检索协议增补"扩展输出规则"；
4. 回归：改动前后各跑 `python eval/run_eval.py` 对照；
5. 每批流程：命中案例 → 附"关联参考"区（暂不影响 `[检索: CASE-xxx]` 标注本身）。

## 5. 若暂不采纳 —— 再评估信号

- 案例库规模上去后人工翻库明显耗时（约 >30 条时重估）；或
- 跨簇时序配对证据确凿（PAT-001 波次配对确认）；或
- 出现"漏关联导致结论偏差"的实际实例。
