## 问题一：模型如何识别、提取实体与关系？无关内容能否剥离？

### 1.1 先厘清：提取在哪一步发生、由谁做

当前项目里"提取"是 Agent（LLM）在做：日志 → 检索 → 判断 → 写案例。在实体模型里，这一步要产出的是**规范化实体 + 实体间关系**，而不只是案例文本。

所以问题一真正问的是：**从一条混杂日志里，LLM 凭什么识别出"这是攻击行为实体、那是噪声"？**

### 1.2 日志里"无关内容"的真实分类（用项目真实日志举例）

以 `data/incoming_logs.txt` 真实行拆解：

| 类别 | 实例 | 与攻击判定的关系 |
|---|---|---|
| 协议元数据 | `Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...`（UA）、referer、时间戳 | 绝大多数无关；**但 UA 偶尔是特征**（某工具固定 UA），所以"无关"是有条件的 |
| 进程载体链 | `<== /bin/bash -c 'cat /etc/passwd' <== /opt/app/main` | 是**上下文**（攻击在哪个进程执行），不是行为实体，但对落地证据有价值 |
| 冗余/包装字段 | 样板行重复的 `/bin/cat cat /etc/passwd`、RASP 的 JSON 字段名 | 无关噪声 |
| 真正的行为实体 | `whoami`、`net user /add`、`wmic /node:{ip} process call create`、路径穿越、`rO0AB` | 攻击行为本体 |

**关键**：噪声和实体**没有固定的字段边界**——`Windows NT` 在 UA 里是噪声，但如果它出现在某攻击工具的固定 UA 里就是特征。所以"剥离无关内容"不是一个简单的字段过滤。

### 1.3 模型能剥离什么、不能可靠剥离什么（诚实回答）

**能可靠剥离的**：显性噪声（UA、时间戳、协议包装）——有明确 schema 边界，LLM 语义理解足够，且这类噪声能靠字段切分机械挡掉。

**不能可靠剥离的**：隐性噪声（哪些 token 是"判别性特征" vs "偶然共现"）——这需要领域判断，LLM 裸判会：
- **漏提**：把 `whoami` 当无意义参数忽略；
- **过提**：把 UA 里的 `Windows NT` 当实体——这正是 `PENDING.md` §2 通用词泄漏的根源（`Windows` 命中 CASE-007、`process`/`select` 经多通道累计到强档）。

**结论**：LLM 的语义理解能剥离"明显无关"，但**不能可靠地**剥离"隐性无关"。把剥离责任全押在模型判断上，就是通用词泄漏这类精度缺陷的温床。

### 1.4 正确做法：剥离靠"结构分层"，不靠"模型裸判"

三层提取，各司其职：

```
① 确定性层（schema 切分 + 正则锚点）——先做，挡掉 80% 噪声
   · 按日志 schema 切字段，把"协议元数据"与"行为载荷"物理分开
   · 用 pattern_probes（已有）做确定性锚点：正则命中的 = 确定性实体，直接提取，无需模型判断
   · 可回归、可单测、可解释
② 语义层（LLM）——只兜底未见形态
   · 仅处理正则覆盖不到的新行为段
   · 产出必须带证据引用（引用日志具体 token），标"待确认"，进人工确认闸门
③ 隔离层（降权，不删除）
   · 无关内容不进实体层，但降权存进案例 notes/aux
   · 理由：UA 今天无关、明天可能是某攻击者指纹；进程载体今天无关、复盘时是落地证据
```

**"剥离"的正确语义是"不进入实体层"，不是"删除"。**

### 1.5 额外：稳定性靠"确定性覆盖率单调递增"

比"能否剥离"更棘手的是 LLM 提取的**稳定性**（同类日志两次提取粒度不同）。解法是一个循环：

> 新形态第一次出现 → LLM 提取 + 人工确认 → **确认后沉淀为新正则** → 下次同类走确定性层。

这样确定性层的覆盖率随库增长**单调递增**，实体提取的稳定性**不降反升**——直接回应了你上一轮"大量数据时出错率会不会升高"的隐忧：出错率不随规模升，反而随正则积累而降。

### 1.6 关系的提取（简述，上一份已详述）

- **时序边**（谁先谁后）：机器从时间戳生成，**易得但噪声大**（并发、乱序、跨源时钟漂移），标"观察级"。
- **逻辑边**（whoami=发现 → net user /add=持久化）：来自 kill-chain 阶段标注，**更有价值但需判断**——走语义层 + 人工确认，与实体同一条"待确认闸门"。

## 问题二：检索命中实体后，如何得到对应的攻击链？

### 2.1 本质：反向映射，链是"引用"不是"重建"

实体图提供的是"实体之间的关联"，但分析者要的是"完整攻击链"。必须回答：命中实体 → 哪条链？

**核心答案：链不是检索时重建出来的，是引用出来的。** 因为链在**入库时就已经作为"有序实体序列"完整保存**了（`ENTITY_VS_CASE_GRAPH.md` §5.2.1 的"案例 = 有序实体序列"）。实体图只负责给你一个**"哪些链包含这个实体"的索引**。

### 2.2 存储时必须显式保留的两样东西

1. **链本体**：案例 = 有序实体序列 `[e1, e2, ..., ek]` + 案例元信息（来源、结论、证据）。
2. **实体 → 案例反向索引**：每个实体节点记录它**属于哪些案例 + 在链中的第几步**。

```
实体 e（如 wmic /node:{ip} process call create）
  └─ case_refs: [ {case: CASE-001, pos: 2}, {case: CASE-001, pos: 2, ...}, ... ]
```

两样东西由**同一次提取动作**写入，保证一致——实体一被提取，就立即登记到它所属的链和反向索引里，不存在"提取了实体却不知道它属于哪条链"的缝隙。

### 2.3 检索流程走查（用真实数据）

```
查询日志: wmic /node:10.20.9.77 process call create "cmd.exe /c whoami" ...
  │
  ├─ 提取查询实体（确定性层参数化）: wmic /node:{ip} process call create {cmd}
  ├─ 命中实体节点（精确匹配）
  ├─ 查反向索引 → case_refs = [CASE-001]
  └─ 取出 CASE-001 的完整实体序列（预存的链）→ 呈现
```

这和当前 `src/retrieve.py` 的"日志行 → 命中案例 → 返回案例"是**同一个逻辑**，只是中间多了一层参数化实体，用来解决"基础设施更名后仍能命中"的泛化问题（IP 从 10.20.6.179 换成 10.20.9.77，实体仍命中，因为 IP 被参数化了）。

### 2.4 三个真正的难点（这才是问题二的实质）

映射本身简单，难在以下三点：

**① 一个实体命中多条链 → 排序**

`cmd=id` 这个实体出现在 CASE-006 / 016 / 022 多条链里。命中它 → 返回多条链，如何排序？

- 排序信号：命中实体在该链中的**角色权重**（核心载荷 vs 次要探针）、命中的实体数量、链的完整度。
- 比案例级检索**更好排序**：实体命中是精确的、可解释的——"CASE-006 排前，因为它命中了你的持久化实体 X"，而非模糊的"整体相似度"。

**② 命中链的中段 → 标注命中位置**

只命中某链的第 3 步（持久化实体），但该链前段是侦察、后段是横向。整条链摊开会让分析者误以为全链都相关。

- 解法：呈现时**标注命中位置**（"你命中的是该链第 3 步"），并区分"命中步"与"上下文步"。
- 这其实是实体模型的**新能力**：局部匹配 + 位置标注，案例级检索做不到。

**③ 链完整度差异 → 证据从严标注**

有的链实体全、有的因日志截断只见到部分阶段。必须标链的"证据完整度"，不全的链注明"仅见 XX 阶段，无后续证据"——这正是 CASE-003 已经在做的证据从严标注（"仅见 LFI 阶段，未含 JS/SSRF 载荷证据"），实体模型把它变成结构化的链级字段。

### 2.5 附带的进阶能力（可选，先提不展开）

实体命中的时序边下游可以**预测下一步**：命中持久化实体 → 该实体在其它链里的后继实体提示"通常接下来是横向移动"。这是案例级检索没有的（案例级只有"相似链"，没有"步骤级转移"）。属加分项，不是问题二的核心。

## 三、两个问题指向同一个设计结论

"进"（提取）和"出"（映射）其实是同一枚硬币，共同指向：

> **实体的提取、链的保存、反向索引的登记，必须在同一次写入里完成，且都"确定性优先"。**

- 进：确定性层（schema+正则）提实体、语义层（LLM）兜底、无关内容降权不删除、新形态沉淀为正则。
- 存：同时写"链（有序实体序列）"与"实体→链反向索引"，由同一次提取生成，天然一致。
- 出：命中实体 → 反查索引 → 取出预存链 → 标注命中位置与证据完整度 → 排序呈现。

这三个环节串起来，就是"实体图 + 案例视图"双层模型的完整工作方式——实体层负责**泛化的命中与关联**，案例层负责**完整的上下文与呈现**，中间靠反向索引衔接，没有"实体提到一半链断了"的缝隙。
