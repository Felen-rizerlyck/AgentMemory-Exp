## 4. 高优先级问题

### H1. `session` / `agent` scope 会拦截其他 session / agent

- check：`scope.session`、`scope.agent`
- 预期（设计 §13）：`session` 只在本 run 生效，`agent` 只对单个 Agent 生效。
- 实际：`scope` 只是一个字符串分类，`preflight` 的过滤条件是 `issue.scope in ("global", request.scope)`，**不比较 `session_id` / agent 身份**；issue 里也没有 `session_id` 字段。
- 证据：session-a 失败一次后，session-b 的 preflight 返回 `block`，reason 为 `blocked until retry window ...`。agent 同理。
- 影响：一个会话里的临时限流/超时会把所有并发会话一起拦住；这是“记忆污染”的反向版本——本该隔离的问题泄漏到全局。
- 建议方向：把 `session_id`/agent 身份纳入 issue 可见性判断（或纳入 fingerprint 的一部分），而不是只存 `scope` 分类。

### H2. 模型 override 可以绕过非重试的 `auth` 拦截

- check：`mode.override_auth`
- 预期（设计 §7.3、§9.3）：`auth` 非重试；模型 override 只有在“已到 `next_retry_at` / `stale` / 人工或策略显式允许”时才应放行。
- 实际：`preflight(..., allow_probe=True, override_basis="model wants to retry")` 对任意 `block` 都返回 `probe`，并把 issue 设为 `probing`；唯一要求是 basis 非空。
- 证据：`blocked=block` → `override=probe`；`issue_status=probing`；`overrides=1`。
- 影响：模型可以绕过“需要人工处理”的认证/权限问题，形成自我解锁；审计记录有了，但 gate 条件没有。
- 建议方向：在 override 分支检查 `now >= next_retry_at` 或 `status == stale`，或要求一个独立的、非模型来源的授权标记。

### H3. 模型 override 也可以绕过 per-run 硬预算

- check：`mode.override_budget`
- 预期（README/§8.3）：per-run 预算是 in-session 的硬保护，超过后返回 `block`。
- 实际：预算 block（`issue_id=""`）同样被 `allow_probe` 改成 `probe`；override 记录里 `issue_id` 为空，且执行后没有 issue 可跟踪。
- 证据：`blocked_reason="run budget exhausted: 1 failure(s) ..."` → `override=probe`。
- 影响：预算是“硬”的，但模型可以把它变成建议；与 H2 是同一根因（override 没有 gate）。
- 建议方向：override 只对 issue 型 block 生效；预算型 block 不应被模型 override，或需要人工/策略授权。

### H4. Windows 下 JSONL 文件锁在并发时会抛 `PermissionError`，并丢行

- check：`store.lock_contention`（高）、`store.multiprocess`（中）
- 预期：README 称 JSONL 使用跨平台文件锁；锁竞争应等待（`FileExistsError` → 重试），而不是崩溃。
- 实际：T6 的 2 进程 × 每进程 100 行 append 只写入 **165/200** 行，并抛
  `PermissionError: [Errno 13] Permission denied: ...\events\2026-11.jsonl.lock`；
  deep 的 8 线程 × 10 次突发测试也能复现（本轮第 4 轮 80 行只写入 72 行）。
  另外，多进程 `issues.json` 的 `temporary.replace(path)` 在 Windows 上还可能抛
  `PermissionError [WinError 5]`。
- 根因：`store.file_lock` 只捕获 `FileExistsError`；Windows 上 `os.open(O_CREAT|O_EXCL)`
  在创建/删除竞争窗口可能返回 Access Denied（`PermissionError`），于是直接冒出；
  `atomic_write_json` 的 replace 也没有并发重试。
- 影响：并发记录时既可能丢 trace，也可能让调用方看到未处理异常；对 harness/gateway 是可靠性问题。
- 建议方向：把 `PermissionError`（以及 `OSError` errno 13/17）也当作“锁被占用”处理，重试到 timeout；更进一步，`issues.json` 的读-改-写也需要锁或单写者队列。
- 说明：这是本机（Windows/Python 3.14）复现；不是每次必现，但突发测试可稳定触发。

### H5. JSON 格式的秘密不会被脱敏

- check：`security.redaction_json`
- 预期：`password`、`token`、`api_key`、`Authorization` 等不应以明文进入 `message_redacted`。
- 实际：`redact('{"password": "hunter2", "token": "tok-abc", "api_key": "AK-123"}')` 原样返回；`{"Authorization": "Bearer abc123"}` 也原样返回。
- 原因：现有正则要求 `password\s*[=:]`（等号/冒号前不能有 JSON 引号），因此 `"password": ...` 这种 JSON 形式漏掉。
- 影响：工具错误消息经常是 JSON；真实 token/密码可能被持久化，并在后续报表/排障中被看到。
- 建议方向：增加 JSON 键值形式的规则（允许引号、单引号），或对解析出的字段做递归脱敏。

### H6. URL userinfo 凭据通过 `target` 泄漏

- check：`security.target_credentials`
- 预期：`https://user:password@host/...` 中的密码不应出现在 issue、decision reason、report 中。
- 实际：`issue.target`、`preflight().reason`、`report.top_open_issues[].target` 都包含 `hunter2`：
  `https://user:hunter2@10.0.0.1/hunt`。
- 原因：fingerprint 会规范化掉 userinfo，但 issue/decision/report 保存并展示**原始 target**；`redact` 只作用于 message。
- 影响：任何把凭据放进 URL 的工具调用都会把密码写进运行记忆和报表。
- 建议方向：落盘 target 前移除 userinfo（或统一走 `redact`），fingerprint 继续使用规范化后的地址。

## 5. 中优先级问题

### M1. 全局 issue 不能被 session 的成功解决，反而卡在 `probing`

- check：`scope.global_resolution`
- 场景：global 失败 → 到期后 session preflight 得到 `probe` → session 调用成功。
- 预期（设计 §7.3）：另一个 scope/agent 的成功至少应 `mitigated`，不应直接 `resolved` 全局；但不能把全局 issue 留在 `probing`。
- 实际：`_resolve_keys` 要求 `issue.scope == request.scope`，所以 session 成功无法处理 global issue；状态停在 `probing`（等待 probe 超时后才回到 open）。
- 影响：一次成功探测不能结束全局问题，后续会重复 probe/block；与“成功可来自另一个 scope”的设计相矛盾。
- 建议方向：跨 scope 成功走 `mitigated`（而不是 `resolved`），并记录来源；或把全局 issue 的“成功”与“同环境成功”分开展示。

### M2. 同名操作的 global 与 session 失败会混成一条 issue

- check：`scope.mixed`
- 场景：同一 fingerprint 先 global 失败，再 session 失败。
- 预期：两条 issue（不同 scope），或至少 scope 信息不被覆盖。
- 实际：`find_issue` 只按 `fingerprint + error_class` 查找，忽略 scope；结果为 1 条 issue，`scope=global`、`count=2`。
- 影响：session 的失败会污染全局计数；后续无法区分“全局确认”与“单会话临时问题”。
- 建议方向：`find_issue` 匹配时带上 scope（以及未来的 session/agent 身份），或在合并时明确升级规则。

### M3. 对已过期 issue 做 `mitigated` 会被下一次 preflight 立即改回 `stale`

- check：`state.mitigated_expired`
- 场景：issue 已过期 → `resolve(..., resolution="mitigated")` → 下一次 preflight。
- 实际：`resolve` 后 status=`mitigated`，但 `expires_at` 仍在过去；`_refresh_issues` 看到 `mitigated + expired` 后改成 `stale`，preflight 返回 `probe`。
- 影响：人工刚刚确认的 workaround 会在下一次调用时被静默撤销；用户看不到“已缓解”的提示。
- 建议方向：`resolve(mitigated)` 时刷新/延长 `expires_at`，或明确文档化“mitigated 也受原 TTL 约束”。

### M4. 类级 `max_attempts_per_run` 未生效

- check：`state.per_class_run_budget`
- 预期（设计 §10 表）：`unreachable` 每个 run 最多 1 次。
- 实际：把全局 budgets 调大后，同一个 run 内可连续产生 **4 次** `unreachable` 失败（class 配置为 1）；`retry_policy.max_attempts_per_run` 只被写入/校验，运行时没有读取。
- 影响：策略表与实际行为不一致；按类限流会失效。
- 建议方向：在 preflight 的 run budget 判断里同时读取 `policy.class_rule(error_class).max_attempts_per_run`（按 issue/operation 计数）。

### M5. 5xx / errno 型网络错误分类为 `unknown`

- check：`classify.server_errors`
- 实际：`HTTP 500`、`HTTP 503` → `unknown`；`OSError(errno=101/111)` → `unknown`。
- 预期（设计 §8.5）：5xx 属于 `internal`；`OSError(errno=101/111)` 属于 `unreachable`。
- 影响：会落到 `unknown` 策略（固定 60s、最多 1 次），与 `internal`/`unreachable` 的 TTL/预算不同；分类错误会改变封禁时长。
- 建议方向：补 5xx → `internal`，补 `OSError.errno` 判断（101/111）。

### M6. `invalid_args` 的分类上下文在 `postflight` 中不可用

- check：`classify.invalid_args`
- `classify_exception(ValueError(...), {"source": "args"})` 能返回 `invalid_args`，但 `RuntimeMemory.postflight` 没有 `context` 参数，因此 gateway 无法把“这个 ValueError 来自参数校验”传进去；默认得到 `unknown`。
- 影响：模型参数错误可能被当成环境问题，进而错误地封禁端点（设计 §8.5 明确警告的反模式）。
- 建议方向：给 `postflight` 增加 `context`（或 `error_source`）参数，或提供 `error_class="invalid_args"` 的明确入口（现在 CLI 可以显式传，但 library 默认路径不行）。

### M7. 损坏的 event journal 会让 `report` / 带 `run_id` 的 `preflight` 抛异常

- check：`store.corrupt_events`
- 实际：event 文件含一行非 JSON 时，`store.check()` 返回 `journal: ...`，但 `runtime.report()` 和 `preflight(run_id=...)` 都抛 `ValueError`；不带 `run_id` 的 preflight 仍可用。
- 影响：单行损坏会让报表和预算检查不可用；虽然 `check` 能发现，但运行时没有降级路径。
- 建议方向：`read_events` 对坏行跳过/隔离（并计数），或让 report/preflight 把 journal 错误作为受控错误返回。

### M8. shadow 的 `false_blocks` 依赖调用方显式传 `decision`

- check：`report.link`
- 实际：shadow block 后如果调用方只 `postflight(req, "ok")`（CLI `record` 的用法）而不传 decision，`would_block=1`、`false_blocks=0`；报表无法把“被建议拦截但实际成功”关联起来。
- 同时 `report` 没有 `false_block_rate` 字段（设计 §15.1 的指标）。
- 影响：shadow 评估容易低估误拦；CLI 工作流无法产出正确的 shadow 报表。
- 建议方向：把 `decision_id` 作为 `postflight` 的必填/可选参数（或在 request 上挂 pending decision），并增加 `false_block_rate`。
- 关联 check：`report.rate`（GAP）。

### M9. （已按计划对齐）run-budget block 可以没有 `issue_id`

- check：`audit.block_issue`（已改为 PASS）
- 计划 T1 明确写的是“per-run 预算耗尽 → block，reason 含 `run budget`，**可无 issue_id**”。
  因此 `reason="run budget exhausted..."` 且 `issue_id=""` 是计划允许的行为。
- 设计 §16.3 不变量 3 的“每个 block 可追溯到 issue_id”与这个例外冲突；这是**文档口径**
  需要对齐的问题，不是运行时缺陷。

### M10. 非法 target / 非 JSON 参数会让 preflight 直接崩溃

- check：`identity.bad_port`、`identity.non_json_args`（CRASH）
- 实际：
  - `target="http://host:99999/x"` → `ValueError: Port out of range 0-65535`（`urlsplit().port`）；
  - `args={"blob": b"abc"}` → `TypeError: Object of type bytes is not JSON serializable`（`args_hash`）。
- 影响：工具边界上的脏数据会让 gate 崩溃，而不是返回一个 allow/block 决策或受控错误。
- 建议方向：规范化 target 时捕获 `ValueError`；对 args 使用可序列化包装（如 bytes → base64/长度摘要）或返回明确校验错误。

### M11. 多进程同时 `record` 会产生重复 live issue

- check：`store.multiprocess`
- 实际：4 个进程各记录 1 次同一操作，3 轮均得到 3~4 条 issue（本轮 3/3/3 条，每条 count=1），
  而不是 1 条 count=4；其中一轮的 `issues.json` replace 还抛了
  `PermissionError [WinError 5]`，说明原子写在 Windows 并发下也不稳。
- 原因：`Store.upsert_issue` 是 load → modify → save，没有跨进程锁；`find_issue` 在各自进程里都看不到对方尚未落盘的 issue。
- 影响：`issues.json` 出现多个相同 fingerprint 的 live issue；`find_issue` 只返回其中一个，计数/证据被拆分。
- 说明：README 明确是 single-writer 原型；但设计 T12 期望“两个进程同时写 events：无丢行；issues 不出现半写”。半写没有出现（`store.atomic_json` PASS），重复 live issue 出现了。建议至少在 `check()` 里检测重复 live issue，或明确把多进程写入列为不支持。

## 6. 低优先级 / 设计缺口

### L1. 仅设置 workaround 不会进入 `mitigated`

- check：`mode.workaround_only`
- 实际：`set_workaround` 后 status 仍是 `cooldown`，preflight 仍 `block`（但 alternatives 会带上 workaround）。
- 文档冲突：CLI help 说 workaround “does not change status”；README_CN §3.3 / 设计 §7.2 说 `open --workaround--> mitigated（allow_with_hint）`。
- 影响：模型能看到替代方案，但仍被硬拦；如果这是有意的“workaround 只是提示”，需要把 README 改一致。

### L2. 观察：`preflight(record=False)` 仍会持久化过期的状态刷新

- check：`state.read_only`（按计划 T1 为 PASS）
- 计划 T1 的要求是“不写 decision、不改 probing”；本项满足：没有 decision 行，
  也不会进入 `probing`。
- 额外观察：issue 到期后 `_refresh_issues` 会把 `cooldown` 改成 `stale` 并落盘；
  对“只读检查”的调用会改变存储。属于设计/语义观察，不是计划失败。
- 建议方向：如需严格只读，可在 `record=False` 时只返回内存中的 refresh 结果。

### L3. `probe_after_expiry=false` 被忽略

- check：`state.probe_after_expiry`
- 实际：配置 `defaults.probe_after_expiry=false` 后，过期 issue 仍返回 `probe`。
- 影响：该配置项没有实际作用；如果用户想“过期也不 probe”，无法实现。

### L4. `policy.defaults` 的 `cooldown_s` / `issue_ttl_s` 不生效

- check：`state.defaults`
- 实际：把 defaults 改成 1s 后，`unreachable` 的 `next_retry_at` 仍是 +900s，`expires_at` 仍是 +86400s（来自 class 配置）。
- 影响：配置表面有 `defaults`，实际只有 class 值生效；容易误导调参。

### L5. 指数退避没有 jitter

- check：`state.jitter`
- 实际：`timeout` 前三次退避精确为 30 / 60 / 120 秒。
- 设计 §10.2 要求 ±20% jitter；当前实现没有，多个 Agent 同时重试会产生同步尖峰。

### L6. 另一个环境的成功不会 `mitigate`

- check：`scope.cross_env_mitigation`
- 实际：lab-a 失败、lab-b 成功后，lab-a 的 issue 仍是 `cooldown`。
- 设计 §7.2 有 `open --other environment success--> mitigated`；当前实现没有跨环境关联（fingerprint 含 environment_id，成功找不到另一个环境的 issue）。

### L7. `duplicate_attempts` 不是按 run 统计

- check：`report.duplicate_scope`
- 实际：两次失败分属两个不同 run，`duplicate_attempts=1`。
- 设计 §15.1 定义为“同 fingerprint 在 run 内”；当前 report 跨所有 run 计数。影响指标口径，不影响功能。

### L8. `check()` 不校验 `expires_at` 不变量

- check：`audit.expires_at`
- 实际：一条没有 `expires_at` 的 issue，`store.check()` 返回 `[]`。
- 设计 §16.3 不变量 4 要求 `expires_at` 一定存在；`check` 只校验“如果有值是否 ISO”，没有校验必填。

### L9. `rebuild_issues` 未实现

- check：`audit.rebuild`
- 设计 §11.6 建议从 events 重建 issues；当前 `RuntimeMemory` 没有该方法。属于 Phase 3 能力，当前不影响主流程。

### L10. 其他未使用的配置项（静态审计）

- `budgets.max_blocked_calls_per_run`：只在 `policy.py` 的默认值中出现，`runtime.py` 没有读取；设置它不会改变行为。
- `classes.*.max_attempts_per_run`：写入 `retry_policy`，但运行时未读取（见 M4）。
- `defaults.cooldown_s` / `defaults.issue_ttl_s` / `defaults.max_attempts_per_run` / `defaults.probe_after_expiry`：未生效（见 L3/L4）。
- 建议：要么接上，要么从 policy 中删除，避免“看起来可调、实际无效”。

## 8. 通过项（32 个）

- **模式**：shadow 记录但不阻止；enforce 阻止并拒绝为被 block 的调用写 postflight；probe in-flight 阻止第二次探测；probe 成功解决 / 失败重开；手动 resolve 后重新打开；mitigated + workaround 返回 `allow_with_hint`；override 有审计记录；从 `data/policy.json` 加载 enforce；note 不改变状态。
- **状态机**：cooldown → open；retry window；Retry-After 优先并延长 expiry；auth 到 TTL 后 stale probe；abandoned probe 恢复；attempt budget 最终 block；环境隔离；目标/参数规范化；call-level key 隔离；已知异常分类；header/URL/密码/私钥脱敏；消息截断；`issues.json` 原子写后可解析；`find_issue` 优先 live；`gc` 删除旧事件/已解决 issue 且保留审计；probe success rate；override 审计；resolved 后可被新失败重新打开；schema/invalid_args 只拦坏参数；`record=False` 不写 decision、不进入 probing；run-budget block 可以没有 issue_id（计划 T1 允许）。

## 9. 建议（按优先级）

**P0（安全/授权/可靠性，建议先处理）**

1. **收紧 override**：只允许在 `now >= next_retry_at`、`status == stale`、或显式人工/策略授权时把 block 改成 probe；预算型 block 不允许模型 override。
2. **scope 隔离**：把 `session_id` / agent 身份纳入 issue 可见性（或 fingerprint），确保 `session`/`agent` 不跨会话泄漏。
3. **脱敏**：补 JSON 键值形式的秘密规则；落盘 target 前去掉 URL userinfo。
4. **文件锁**：`file_lock` 捕获 `PermissionError` / `OSError`（errno 13/17）并按竞争重试；`issues.json` 的读-改-写改为单写者队列/锁（或明确不支持并发写并在 `check()` 中检测重复 live issue）。

**P1（行为一致性）**

5. 跨 scope 的成功 → `mitigated`，不要停在 `probing`；`find_issue` 按 scope 隔离。
6. 接入 `classes.*.max_attempts_per_run`；清理/实现 `max_blocked_calls_per_run`、`defaults.*`、`probe_after_expiry`。
7. `resolve(mitigated)` 刷新 TTL；或文档化“mitigated 也受原 TTL 约束”。
8. 补 5xx / `OSError.errno` 分类；给 `postflight` 增加参数上下文。
9. 损坏 event journal 的降级路径；非法 target/args 的受控错误。

**P2（指标/健壮性/文档）**

10. shadow `false_blocks` 的 decision 关联与 `false_block_rate`；`duplicate_attempts` 按 run。
11. `check()` 校验 `expires_at` 必填；设计 §16.3 不变量 3 与计划 T1 的“预算 block 可无 issue_id”对齐措辞。
12. 指数退避 jitter；`rebuild_issues`（可后置）。
13. 同步 README_CN/CLI 关于 workaround → mitigated 的描述。

以上都**没有**在本轮直接改算法；是否符合预期需要产品/维护者决策。
