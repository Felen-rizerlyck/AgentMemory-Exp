## 摘要

- **公开记忆基准的数字不可跨厂商比较，且分歧已经进入公开互诉**：同一基准、同一对手系统，分数在一年内依次出现 84% → 75.14% → 58.44%，每一步都伴随方法学指控（[I-07]、[I-08]）；Mem0 与 Zep 各自的 LoCoMo 口径（读模型、判模型、检索预算、context 大小）逐项不同，1.5–2.2 分的差距落在口径差异量级内（[I-04]）。
- **"图"在头部厂商自己的数据里只值约 2%**：Mem0 论文自报带图变体总分仅高约 2%，单跳为负增益、多跳零增益，只有时序类受益（[A-14]）；Zep 自述其检索同时持有向量与 BM25 索引（[I-04]）；而"只保留合并/替代/矛盾三类关系 + 一跳扩展、不建全图"的轻量方案在同 backbone 下取得最好成绩且运行时间大降（[A-02]、[A-03]）。
- **向量层是否必要是"工作负载属性"，不是普适结论**：同一套检索底座在 LoCoMo 上由 BM25 单通道最强、稠密通道 100% 可跳过，在 LongMemEval 上稠密通道确有增量信息、仅跳过 63% 的查询（[A-01]）。
- **存在明确的反向证据**：一个刻意非向量的本地优先架构，在 LongMemEval 公开端点上落后纯 vector-RAG 22.0 / 26.5 个百分点，且作者自己的机制保真审计承认"图结构效用未被证明"（[A-05]）。这是"零向量库"路线必须正面回应的一条。
- **"检索到了"与"用对了"必须分开度量**：某个公开冲突更新切片上 22 个已报告系统的多跳成绩全部 ≤7%，而把"证据识别"与"策略执行"解耦后单跳达 82%/93%，其中仅替换最后的策略执行器只贡献 2.0 个百分点（[A-04]）。
- **写入与保留策略比检索算法更能决定不可逆损失**：在 top-k 检索 + 80k 预算下，可被修正的错误中不可逆占比 0.67–0.73（[A-09]）；且同一论文明确指出"预算—准确率曲线不声明检索机制就不可比较"。
- **投毒是产品化的硬约束**：1.2% 的投毒语料把 LongMemEval 准确率从 0.850 打到 0.300，而同一套写时内容筛查对 360 条投毒记忆**拒绝 0 条**（[A-06]）；工业侧同向——"记忆进系统提示"是已被走通的持久攻击路径（[I-10]），厂商给出的对策是类型化写入、先过滤后排序、记忆不进系统提示（[I-06]）。
- **零向量库不是权宜之计，而是已被交付的产品默认形态**：Letta 明写其 MemFS 默认不含语义/向量索引（[I-01]）；Claude Code 的记忆是纯文本文件、按路径寻址，并给出"每个文件目标 200 行以内"的经验上限且承认超限会降低遵循度（[I-02]）；一个 8.5k star 的 Rust 记忆服务把"何时才该加 `sqlite-vec`"写成可执行触发条件，并以**零 LLM 的纯 FTS** 在 LongMemEval-S 上取得 hit@1 0.534 / hit@5 0.668（[O-01]）。

**总体判断**：本次调研支持"现阶段不必上向量库或图库"这一结论，但支持它的理由与项目文档目前的写法不同——**理由不是"符号检索更准"，而是"公开证据显示向量/图的增益在你们这个规模与工作负载下无法被证明，而它们的代价（写入成本、运维面、攻击面、不可比的口径）是可测的"**。反过来说，同一批证据也给出了必须补的三件事：写入侧的生命周期元数据（时间、来源、活跃标志、槽位键）承载了大部分正确率收益（[A-07]），精度治理是"检索+装配"两段问题而非一段（[A-04]），以及"无匹配内容时应拒答"这一能力在公开基准上被系统性回避（[A-13]、[O-01]、[A-14]）——恰好是本项目前瞻测试里 3/3 失败的那一项。我建议的决策是：**维持零向量/零图库的架构判断，但把下两个迭代的资源从"要不要加图"转到"写入侧元数据 + 装配分离 + 拒答能力"上**；向量层保持 C6/C7 预留位，并以查询类型分层的测量（而非整体召回）来决定何时启用（[A-01]、[O-01]）。

## 1 调研问题与方法

### 1.1 课题界定

- **问题**：以本项目「符号化案例记忆 + 轻量关系层（零向量库、零图库）」为对照基准，业界（学术机制、Agent Memory 产品与标准、开源项目）在记忆的**写入—检索—关系—评测**四环上的做法与边界分别是什么；哪些外部证据支持或反驳"现阶段不必上向量库/图库，但必须治理检索精度"这一判断。
- **范围**：时间窗以 2024-09 至 2026-09 为主（个别奠基工作如 LoCoMo 2024-02 例外）；中英文皆采（实际命中以英文为主）；场景聚焦可长期运行的 Agent 记忆系统，并包含安全检测/日志复用的邻近形态。
- **深度**：选型比较型（决策支撑）。每条结果 150–300 字，四段式：做了什么 → 怎么做的 → 结果及其条件 → 意义与局限。
- **排除项**：模型自身的长期上下文与位置编码类研究（长上下文注意力、KV cache 压缩）；纯向量数据库的功能与跑分横评；通用 RAG 基础设施评测（含通用 RAG 语料投毒一族）。

### 1.3 评价标准

按贡献（0.30）、意义（0.25）、时效（0.20）、置信度（0.25）四维打分，`总分 = 0.30×贡献 + 0.25×意义 + 0.20×时效 + 0.25×置信度`，满分 10 分。

时效按本课题自身节奏校准：**记忆系统领域在 2024-09 之后迭代极快（基准、模型栈、厂商口径在 12 个月内多次更换）**，因此 2026 年产出按 10 分、2025 年 8 分、2024 年 6 分、2023 年及更早 4 分起步，再按"结论是否已被后续工作取代"微调。置信度按证据强度给分：同行评审 + 多源印证 8–10；官方一手文档 7.5–8.5（页面无日期者扣分）；高质量预印本且代码公开 5.5–6.5；厂商自评且无第三方复现 4–6；纯营销口径 1–3。

## 2 学术线索结果

### 2.1 检索机制：向量层到底什么时候才必要

**[A-01] AgentIR: A Workload-Adaptive Cascade Retrieval Substrate for Long-Term Conversational Memory**（arXiv:2605.25092，2026-05-24，预印本，评分 7.65）

- **做了什么**：把"用哪种融合方式"从固定配置改成**每查询决策**，并额外决定"这次是否值得跑稠密通道"。
- **怎么做的**：在 BM25 / Dense / RRF / agent-aware RRF 之间按查询选择；用**置信度触发的级联路由**，仅凭 BM25 top-k 的间隔判断是否跳过约 52ms 的稠密通道，跨工作负载重调而不重训；底层是时间分区索引。
- **结果**：**在 LongMemEval（n=500）上稠密通道确有增量信息**，级联跳过 63% 查询、在 LLM 判定准确率持平下快 2.67 倍（按查询类型设阈后 5.76 倍）；**在 LoCoMo（n=1,982）上 BM25 单通道本身就是最强单系统**，同一触发器自动收敛到 100% 跳过稠密通道（快 132 倍，Hit@5 +0.089）。共享 8 核机器上并发 agent 数由约 154 升至约 1,400。
- **意义与局限**：这是本次调研中把"要不要向量"从立场问题变成**工作负载测量问题**的最直接证据，也说明该按查询类型分层测量而非只看整体召回。局限：作者自建系统、无第三方复现；其检索层指标（Hit@5）与厂商的端到端 LLM 判定数字**不可直接比大小**。我的评价：这条应当直接覆盖本项目的"补测 3"，把它从一次整体测试改造成按查询类型分层的测试设计。

### 2.2 关系层：从全图到三关系一跳

**[A-02] MemoryLACE: Memory Lifecycle-Aware Consolidation and Evidence Retrieval**（arXiv:2609.03201，2026-09-02，预印本，评分 7.80）

- **做了什么**：论证"只显式建模局部证据生命周期"就足以显著改善长期记忆推理，**不需要完整知识图、也不需要全局反思**。
- **怎么做的**：每条记忆是六元组（独立复述的证据文本、时间元数据、轻量元数据、来源轮次、活跃标志、生命周期关系集）；关系**只有三类**：merge（重复）、update/supersession（同期状态变化）、contradict（范围内不相容，**保持双方活跃**）。写入按时间序处理，先语义+同实体取候选、再扩展**一跳**生命周期邻居，用 cross-encoder 重排决定"哪些进入比较"（重排不决定关系），一次决策只选一个关系-目标对。检索从活跃记忆作锚点做生命周期扩展与关系感知重排。
- **结果**：摘要口径为在 BEAM 与 StructMemEval 上同 backbone 比较**总体最好**，BEAM 端到端运行时间相对最强反思式基线 Hindsight **降低 66.6%**；消融显示生命周期扩展与时间感知是主要贡献来源。
- **意义与局限**：与本项目"符号化案例 + 人工确认一跳边"几乎同构，是"轻量关系层够用"最直接的学术对应物。局限：关系判定仍由 LLM 决策（**粒度漂移问题未被正面处理**）；矛盾保持活跃等于写入侧不消解冲突，其评测后果未被单独检验；我（本次）只读到方法与架构章节，66.6% 与"最高"的基线集合未能核；无公开代码。

**[A-03] Grounded Continuation: A Linear-Time Runtime Verifier for LLM Conversations**（arXiv:2605.14175 v2，2026-09-09，预印本，代码公开，评分 8.20）

- **做了什么**：把"关系层"实现为**一张带 standing 标签的依赖表**，而不是图数据库。
- **怎么做的**：LLM 只做一件事——把每句话分类为八种认识论操作（Observe/Hypothesize/Support/Undermine/Revise/Expand-Awareness/Resolve/Question）；一个**符号引擎**把这些操作施加到 dependency map 上（认识论可信度模型 + 带 active/weakened/abandoned/resolved 标签的论辩框架 + 公开承诺集 + 依赖映射）。groundedness 检查与撤回查询都是**对该结构的线性遍历，零 LLM 调用**，且撤回满足 conflict-free 保证（撤回一个前提只移除恰好依赖它的结论）。
- **结果**：在信念修正基准与 MemoryAgentBench 的 fact-consolidation 分片上超过预算匹配的 transcript-RAG 基线，把该分片单跳从 0.46–0.95 提升到 0.93–0.98；加了验证器后最弱的 7B 模型超过未加验证器的 GPT-4o；每查询成本与对话长度无关（prompt 稳定在约 0.8k token，而全上下文方案 66k–114k）；2000 轮时撤回查询 <1µs。
- **意义与局限**：它把"轻量关系层"的形态具体化到可实现的程度，并**免费提供精确撤回语义**——正对本项目 S4 的可删除性缺口。局限：前提是每句话可归入八类之一；基准自带结构化更新元数据（作者用 GPT-4o 抽取做了缓解实验）；我只读到方法与形式化章节，命题证明与全部数字未核。我的评价：若本项目要把"一跳边"升级，**升级成依赖/撤回关系比升级成图库更有证据支撑**。

**[A-04] Reliable Post-Retrieval Assembly for Agent Memory: Separating Evidence Extraction from Policy Execution**（arXiv:2606.01435 v2，COLM 2026 Lifelong Agent Workshop poster，代码公开，评分 8.18）

- **做了什么**：把"后检索装配"当作独立可靠性边界，量化"检索到了"与"用对了"的差距。
- **怎么做的**：让 LLM 先把语义匹配的证据抽取为候选表示，再由一个独立阶段执行所需答案策略（如"取更新的那条"），从而把语义过滤、冲突消解、旧值抑制与最终生成解耦；在 MemoryAgentBench v3 的 FactConsolidation 分片与 LongMemEval 上做受控全流水线比较（相同 backbone、相同 top-10 证据、相同分块）。
- **结果**：该分片明确声明"序号越大越新"，但**已报告的最好结果仅 54% 单跳，全部 22 个已报告系统的多跳 ≤7%**；解耦流水线在 262K 下达 82%/93% 单跳（gpt-4o-mini/gpt-4o）与 27%/41% 多跳。受控比较：单跳平均提升 10.8 个百分点，而**仅替换最终策略执行器只贡献平均 2.0 个百分点**（262K 处为 0）。LongMemEval 上无显著整体优势（26/45 vs 29/45，p=0.45），作者据此把结论限定在"带显式版本元数据的当前值问题"。
- **意义与局限**：这是"该花力气治理检索与装配精度、而不是替换存储层"的量化支撑，并给出一个可引用的公共天花板（多跳 ≤7%）。局限：workshop poster 未经主会评审；作者自我限定范围；我未读到受控实验的统计细节。

### 2.3 写入、代价与风险：三个被低估的约束

**[A-05] LSREP: A Longitudinal State-Replay Protocol for Evaluating Conversational Memory, with ICE v2 as an Audited Local-First Architecture**（arXiv:2609.16730，2026-09-15，预印本，代码与冻结快照公开，评分 8.45）

- **做了什么**：**本报告中最重要的反向证据**——一个刻意非向量的"本地优先"记忆架构作者，公开报告自己输给了纯向量 RAG。
- **怎么做的**：提出纵向状态重放协议（有序重放 + 显式生命周期计划 + 重复探针 + 演进中的参考答案 + **机制保真检查**）；以其自研 ICE v2（类型化存储、检索融合、动态上下文预算）为审计案例：私有单用户实例含 1,985 轮、219 个探针、52 个检查点上的 1,211 次观测；另有 LongMemEval 的公开端点对照诊断。
- **结果**：在 LongMemEval 的匹配公开诊断中，ICE v2 明显输给纯 vector-RAG——evidence-only oracle **50.8% vs 72.8%**，full-S **43.0% vs 69.5%**，配对差分别为 -22.0（95% CI [-26.6, -17.4]）与 -26.5（[-31.3, -21.8]）个百分点，伴随保守拒答与严重的多会话/时序失败；在三个"普通密度"数据集上与 vector-RAG 平均质量差接近零且少选 32% 片段，但多耗约 6.6% prompt token。作者自己的机制保真审计承认：**程序性检索本身有缺陷、若干机制未被触发、图结构的效用未被证明**。
- **意义与局限**：它示范了两件自建评测必须做的事（机制保真检查、公开端点对照），同时是对"零向量库"最有力的反证。局限：单作者；主要实例不可外部复核；审计对象与被比较对象同一（因此可能低估"该架构类别"）；公开对照只用一个基准、一次配置。我的评价：**这条必须写进决策依据的"反方陈述"里**，它把"要不要上向量"的门槛从"哲学争论"变成"你在公开端点上掉多少分、以及你为什么认为你的工作负载不同"。

**[A-06] Utility Under Attack: Agent Memory Poisoning and the Limits of Content Screening and Provenance Ranking**（arXiv:2608.21230，2026-08-21，预印本，评分 8.33）

- **做了什么**：把防御目标从"降低攻击成功率"改成"被投毒后记忆还剩多少价值"，并给出投毒比例—效用曲线。
- **怎么做的**：威胁模型取最弱形态——攻击者只能通过非信任通道写内容（浏览网页、工具返回、共享命名空间），知道 agent 大致会被问什么并据此措辞但**不做任何优化**；系统自带四阶段写时内容筛查、以及"语义相似度 + 来源先验"加权的读时排名器。
- **结果**：**1.2% 的投毒语料把 LongMemEval 准确率从 0.850 打到 0.300**（抹掉约三分之二效用）；那套写时筛查对间接提示注入召回 0.832、对含触发词的良性文本仅误报 1.5%，但**对 360 条投毒记忆拒绝 0 条**；随版本发布的来源权重与"无防御"统计上不可区分（p=0.80），提高权重后防御生效但机制变成**排除而非偏好**；当承载答案的证据本身来自非信任通道时，120 个问题中无一条证据记忆能通过排序，准确率跌到 0.0417。
- **意义与局限**：这条攻击**没有 payload、没有指令、没有触发词**，因此"写时内容筛查"是结构性盲区而非检测器不够好——区分真假陈述通常需要文本之外的接地。对本项目的直接推论：安全不能寄托在写时过滤器上，而应落在来源、配额与人工确认。局限：单作者、被评测系统即作者自家系统（自曝负结果）；攻击非自适应，作者自称结果是下界；只在单一基准上做。

**[A-07] Fortunate Recall: Ontology-Driven Memory Lifecycle Management for Persistent Coherence in LLMs**（arXiv:2609.10413，2026-09-09，预印本（作者注明 under review），评分 8.18）

- **做了什么**：用"确定性生命周期策略 + 仅两次 LLM 调用"的结构拿到高成绩，并通过预注册消融回答"到底哪一层在起作用"。
- **怎么做的**：把抽取出的**事实（关系边）**分类到 10+1 个行为类别，类别决定衰减率、替代语义、到期逻辑与检索路由；生命周期层是确定性的闭式 log-score；随时间衰减的半衰期跨 4–19 天；slot-key 替代按归一化 (subject, attribute) 键触发，高置信矛盾把旧边置为非活跃、低置信保留双值软替代；事件时间有效性与前瞻激活分离；类别感知检索路由。
- **结果**：在自建 LifecycleBench（516 题时序消歧）上 76.9%，高于 Mem0 61%、A-MEM 65.3%、MemoryOS 70.5%；完整 LongMemEval-S 500 题 75.2%。**关键消融**：把细分类本体换成三个"通用生命周期原语"+ 仅语义排序器，正确率统计上不变（-1.7pp，95% CI [-6.0, +2.7]），即**承载正确率的是通用生命周期元数据**；细分类本体承载的是**校准**（把下游幻造减半，12.0% vs 24.2%，p<0.001）。端到端上把对照的幻造率从 45.1% 降到 22.4%，同时在独立构建的 BEAM 上复现增益（46.8% vs 32.9%），增益集中在**矛盾消解**。
- **意义与局限**：这是对本项目落地次序最直接的一条指导：**先补通用生命周期元数据（时间戳、来源、活跃/失效标志、槽位键），再考虑细分事实类别**。局限：基准与本体同出一手（自产自测风险，用预注册 + 独立基准迁移缓解）；LLM 抽取的粒度漂移未被量化（三判官一致性仅 κ=0.67）；代码与基准"发表后公开"，当前不可复核。

**[A-08] Graph Memory for LLM Agents: At What Cost? A Comparative Evaluation of Query, Ingest, and Update Performance Across Graph Database Engines**（arXiv:2609.23315，2026-09-20，预印本，评分 7.78）

- **做了什么**：把"要不要上图库"从立场问题转成**成本结构问题**。
- **怎么做的**：构造合成属性图（102 万节点，节点+边 534 万行）与 20 条查询负载，在三档规模上把一家面向本体的列式查询引擎与 7 个目的构建/图扩展型数据库（LoraDB、Ladybug、DuckPGQ、Memgraph、Neo4j、HugeGraph、FalkorDB）对比，报告查询延迟几何均值、批量写入吞吐、点更新延迟、答案正确率，并推导把 ingest/query 权衡表达为查询量函数的 TCO 模型。
- **结果**：**没有系统全面最快**（原生图引擎在窄范围有界邻域上更快；列式在需要扫描或连接大部分图时更快）。**主导成本差异不是查询延迟，而是"让数据变得可查询"的成本**：批量 ingest 吞吐跨三个数量级（5.0k–4.3M 行/秒），交叉点显示在"每次数据刷新少于约 10^5 次查询"的工作负载下 ingest 成本主导总成本。
- **意义与局限**：对"数十个记忆单元"的场景，这句话的含义是——**上图的收益必须在查询侧有极大回报，才能覆盖它自己的写入与运维代价**。局限：**作者与被评测系统同源（利益相关，已披露）**；102 万节点的规模与本项目差 4–5 个数量级，外推必须谨慎；未跑任何 agent-memory 任务。

**[A-09] What Eviction Destroys: A Restore-Counterfactual Audit of Forgetting in Agent Memory**（arXiv:2609.08279，2026-09-08，预印本，评分 8.05）

- **做了什么**：提出"不可逆损失"作为预算—准确率之外的第三种评测口径。
- **怎么做的**：对每个问题做配对干预——把该题 gold evidence 重新注入读时上下文并重跑同一 reader——再结合"该证据在淘汰后是否仍被保留"这一事实，把每个"oracle 可答却答错"的错误分成可恢复、不可逆、残余三类；在 LongMemEval-S 上比较四种淘汰策略在三个 token 预算、两种检索机制下的表现。
- **结果**：80k 预算 + top-k 检索下，可被恢复修正的错误中**不可逆占比 0.67–0.73**（FIFO、随机、冗余感知），LLM 重要性淘汰为 0.60；8k 预算下四种策略均达 1.00；在强制注入 gold 的机制下按构造不存在可恢复错误，因此**预算—准确率结果在未声明检索机制时不可直接比较**；探索性的准确率匹配分析在 1.2–6 个百分点分辨率下未能检出差异（但能检出故意设置的破坏性对照）。
- **意义与局限**：它同时给出两个对本项目有约束力的结论——写入与保留策略比检索算法更能决定不可逆损失，以及**任何"回顾性重放"式自建评测都必须连同检索机制一起报告**（这与项目文档自陈的"回顾性重放只是可达性证据"同向）。局限：单作者预印本；只在单一基准上；主导 reader 为单一模型；方法假设 gold evidence 可被识别并注入，这在开放域不总成立。

**[A-10] Neuromem: A Granular Decomposition of the Streaming Lifecycle in External Memory for LLMs**（arXiv:2602.13967，2026-02-15，预印本，评分 7.30）

- **做了什么**：指出多数记忆评测假设**静态**（离线建库、固定状态查询），而真实场景是**流式**（新事实持续到达、插入与检索交错、状态在服务查询的同时演进），并给出对应的测试床与五维设计空间。
- **怎么做的**：在"插入-检索交错"协议下评测，把外部记忆生命周期分解为五维：数据结构（分区式离散块 vs 层次式显式依赖）、写入归一化（粒度与保真度）、整合策略（冲突消解、容量衰减淘汰、结构精炼）、查询构造、上下文整合（重排或融合）；在同一条服务栈内替换各维度代表变体做受控消融，用 LoCoMo、LongMemEval、MemoryAgentBench 三个数据集报告 token 级 F1 与插入/检索延迟。
- **结果**：作者总结为"**复杂度的守恒**"——系统通常在插入与检索之间**转移**计算债而非消除它；数据结构（是否显式建模依赖）决定可达的准确率天花板；**性能通常随记忆在轮次间累积而退化，且时间相关查询始终是最难的一类**；激进压缩与生成式整合主要是把成本在插入与检索之间搬移，准确率收益有限。
- **意义与局限**：这是本报告对"规模"这一子问题唯一直接相关的学术证据，且对本项目有一句警示：**"记忆越多、精度越低"是被观察到的常态**，与本项目实测的"案例 9→22 时噪声/查询 0.25→0.91"方向一致。局限：我只读到设计与方法章节，"退化"的幅度与曲线形状未经表格核实；三个数据集均为对话/QA 类，与安全日志场景不同；未见第三方复现。

### 2.4 评测方法与基准：口径不可比是系统性问题

**[A-11] Evaluating Memory in LLM Agents via Incremental Multi-Turn Interactions（MemoryAgentBench）**（arXiv:2507.05257 v4，ICLR 2026 Poster，评分 8.60）

- **做了什么**：把记忆评测从"单一问答准确率"改成**四项能力口径**——准确检索、test-time learning、长程理解、**选择性遗忘**——并把已有长上下文数据集改写为"记忆单元被逐步累积"的增量多轮格式。
- **怎么做的**：以记忆科学与认知科学的经典理论界定四能力；把现有长上下文数据集与新构造数据集改造为增量格式；在同一基准上评测从朴素上下文、RAG 到外部记忆模块与工具型 agent 的多类系统。
- **结果**：摘要层面的结论是"**当前方法无一掌握全部四项能力**"；可核的外部数字来自后续工作在 FactConsolidation 分片上的报告——最好结果仅 54% 单跳、22 个已报告系统的多跳全部 ≤7%（[A-04]），而符号验证器可把该分片单跳从 0.46–0.95 提到 0.93–0.98（[A-03]）。条件：该分片自带"序号越大越新"的显式更新元数据。
- **意义与局限**：其中"选择性遗忘"与"test-time learning"正是 LoCoMo/LongMemEval 覆盖较弱的两项，也对应本项目"案例失效"与"库外内容应静默"。它是 ICLR 2026 接收、且被 2026 年多篇工作当作基线的公共刻度。局限：四项能力由论文自定而非社区共识；增量格式与真实日志流的分布差异未量化；我读到的是摘要与 OpenReview 页面，未见分项数字与基线配置。

**[A-12] LongMemEval: Benchmarking Chat Assistants on Long-Term Interactive Memory**（arXiv:2410.10813 v2，ICLR 2025，评分 8.38）

- **做了什么**：给出 500 题的长期记忆基准，并把记忆设计拆成**索引 / 检索 / 读取**三阶段统一框架。
- **怎么做的**：500 道人工精编问题嵌在可自由伸缩的用户-助手会话历史中，覆盖五项能力：信息抽取、跨会话推理、时序推理、**知识更新**、**拒答**；在三阶段框架下做受控实验，提出会话分解（值粒度）、事实增强的键扩展（索引）、时间感知的查询扩展（检索）。
- **结果**：商业对话助手与长上下文 LLM 在"跨持续交互记忆信息"上出现约 **30% 的准确率下降**；上述优化同时提升召回与下游问答。条件：500 题、可扩展历史长度、LLM 判定式评分；基准与代码公开（参考实现见 [O-06]）。
- **意义与局限**："知识更新"与"拒答"被写进公共评测口径的源头，正对本项目的冲突更新与"无匹配即【新案例】"；其"读取/装配"一环最容易被自建评测忽略，而 [A-04] 正是量化这一环的工作。局限：500 题规模小、单题波动影响大；依赖 LLM judge，摘要未交代基线细节；已知其 500 题池被多篇后续工作反复使用，存在同一池反复调参的风险。

**[A-13] Evaluating Very Long-Term Conversational Memory of LLM Agents（LoCoMo）**（arXiv:2402.17753，2024-02-27，评分 7.05）

- **做了什么**：构造超长期对话数据集与配套评测基准，覆盖问答、事件摘要与多模态对话生成。
- **怎么做的**：机器-人混合流水线生成对话，以 persona 与时序事件图接地，并让每个 agent 可分享/回应图像；人工标注者校验长程一致性与事件图接地。数据集每段平均 **300 轮 / 9K token**、最多跨 35 个会话。
- **结果**：LLM 在理解长对话与把握长程时序、因果动态上存在困难；长上下文 LLM 与 RAG 能带来改进但仍显著落后于人类表现（摘要未给量化幅度）。
- **意义与局限**：它是本领域最常被引用的基准，也是 Mem0/Zep 之争的战场。**我核出一处口径不一致值得记录**：Mem0 论文称该数据集每会话约 600 轮、平均 26k token（[A-14]），而原论文自述"300 turns and 9K tokens on avg."，同一数据集两处描述相差近 3 倍。另一条观察：该基准的**对抗（不可回答）类因缺 ground truth 被使用方普遍剔除**（Mem0 与 Zep 双方都剔除，[A-14]、[I-07]），而同样地 LongMemEval 的 abstention 题在一个开源实现的公开记录里也被排除（500 题中只计分 470，[O-01]）——**"无答案/不可回答"这一能力在公开报数中被系统性回避**。局限：合成对话 + 人工编辑，与真实流量分布不同；仅 v1、无勘误版本。

**[A-14] Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory**（arXiv:2504.19413，2025-04-28，厂商自研预印本，评分 6.75）

- **做了什么**：提出 Mem0 与其图记忆变体 Mem0g，并在 LOCOMO 上与六类基线系统（既有记忆增强系统、不同 chunk/k 的 RAG、full-context、开源记忆方案、专有模型系统、专用记忆管理平台）系统比较。
- **怎么做的**：LLM 从持续对话中动态抽取、整合、检索显著信息；图变体在图上表示会话元素之间的关系。指标为 F1 / BLEU-1 / LLM-as-a-Judge（J，10 次运行取均值 ±1SD），评测单跳、时序、多跳、开放域四类问题。
- **结果**（我逐节核读全文）：搜索延迟 p50 0.148s / p95 0.200s、总 p95 1.440s，而 full-context 总 p95 为 17.117s；**full-context 的 J 最高（约 73%），论文原文承认它"can provide a slight accuracy edge"——记忆系统的收益在 token 与延迟（相对 full-context 的 p95 降约 91%）**；Mem0g 以 J=68.44% 为全文最高，但摘要自报**"比基础配置高约 2%"**，且单跳为负增益、多跳零增益，图增益集中在时序与开放域；LangMem 搜索 p50 17.99s / p95 59.82s，论文自称"impractical for interactive applications"。
- **意义与局限**：这是"加图只值约 2%"这一判断的原始出处——**最常被引用为"图有效"的论文，同时是"图增益有限"的证据**。局限（我核出的具体口径问题）：OpenAI 基线的延迟数字**不含记忆抽取成本**（原文明确写它处理的是"manually extracted memories"，且该成本"is not reflected in the reported metrics"），同时该基线在检索侧被"授予全部记忆"（intentionally granting privileged access）；对抗类被整类剔除；厂商自评、无同行评审、无第三方复现；随后被 Zep 公开质疑（[I-07]、[I-08]）。

## 3 工业线索结果

### 3.1 零向量库的产品先例

**[I-01] Letta（MemGPT 系）. MemFS（git 支撑的记忆文件系统，默认无语义/向量索引）**（官方一手文档，`Last-Modified` 2026-09-27；评分 8.93）

- **性质**：官方一手文档（docs.letta.com/concepts/memfs）。
- **可核验内容**：MemFS 是"the git-backed memory filesystem used by Letta agents"，记忆本身属于 agent 状态、存放在属于该 agent 的 git 仓库中，并投影为真实 checkout 供 agent 用**普通文件工具**读写；**"All Letta agents use MemFS."** 记忆按路径寻址（标签 `system/persona` 投影为 `system/persona.md`，选标签即决定它放在哪、是否留在上下文），每条记忆是带 YAML frontmatter 的 Markdown。加载规则：`system/` 下的文件每轮进入系统提示；`system/` 之外的文件不进上下文，但**文件树本身常驻提示，"directory and file names act as signposts"**，内容按需读取。检索（本课题核心）：**"MemFS does not include a semantic or vector index by default. Agents find memory in its Markdown files with normal file-search and read tools."** 关键词搜索无需额外依赖，语义与混合模式需另装 MemFS Search mod 并先对记忆目录建索引；本地后端的会话转录检索目前只有全文匹配。版本化：每次记忆编辑都提交到该 git 仓库，提供版本历史与冲突解决。
- **宣称内容及其基线**：文档为能力描述，无精度数字、有效果声明，故不涉及基线问题。

**[O-01] akitaonrails/ai-memory**（Rust 记忆服务；MIT；默认分支 `main`，`pushed_at` 2026-09-27；评分 8.85）

- **检查版本与方式**：API 路线（元数据 + 完整文件树 877 路径 + 读取 `Cargo.toml`、`docs/vector-backend-policy.md`、`docs/benchmarks/longmemeval-s-2026-09-01-fts.md` 原文）。未取 commit 短哈希。
- **实现了什么**：面向编码 agent CLI 的长期记忆服务。存储为 **SQLite + git 管理的 markdown，markdown 是唯一真相源**；查询路径 `memory_query` 组合 **FTS5 + 词法实体匹配 + 图邻居扩展 + 可选向量 RRF + 原始观察回退**，每条通道经同一有界候选窗贡献，**融合之后**再做一次"页面权威度"调整，使"语义相似度不能单独把某个会话页判定为比一条已维护的决策更权威"。向量以打包向量存于 SQLite、查询时做**暴力余弦**。
- **本次亲验的关键一手材料**（我独立读取并核对原文）：`docs/vector-backend-policy.md` 明确写"**`sqlite-vec` is deferred intentionally, not rejected**"，理由是"expected corpus is usually hundreds to low-thousands of latest wiki pages per project"，并给出**可执行的升级触发条件**：①每项目最新嵌入页数**经常超过约 5k–10k**；②`memory_query` 在 FTS 与图路径已优化后，**p95 仍因向量评分超过约 150–250ms**；③性能分析显示查询时点积消耗可观 CPU（尤其并发 MCP 调用下）；④**真实检索评测显示向量结果相对 FTS5 + 实体 + 图有实质提升，例如 +5–10% recall@5**；⑤迁移可在不重置用户数据的前提下从既有嵌入表回填；⑥派生索引可被丢弃并从 markdown + 嵌入重建，**修复过程绝不删除源 wiki 文件**。并明确列出**非触发条件**："**Do not add `sqlite-vec` just because vector databases are conventional, or because it feels architecturally cleaner.**" 另有一份零 LLM 的公开基准记录（`docs/benchmarks/longmemeval-s-2026-09-01-fts.md`，commit `0ac0dcf8…`，mode: **zero-llm**，470 题计分、**30 道 abstention 题被排除**）：overall **hit@1 0.534 / hit@3 0.647 / hit@5 0.668 / hit@10 0.696**；分片 knowledge-update hit@1 0.583、temporal-reasoning 0.535、multi-session 0.446、single-session-assistant 0.679、single-session-preference **0.300**；注释说明 hit@k 是"任何证据会话进入前 k"（即多数系统公布的 Recall@k），recall@k 是找到的证据会话比例，且**无法归属的页面永不计分**。
- **代码质量与活跃度**：`pushed_at` 为检查前一日；`Cargo.toml` 版本 2.4.1、有 `test-support` 共享测试 crate 与独立 A/B 评测 harness；测试目录成体系（含 `fts_drift_status.rs`、`embed_backfill.rs` 等）。stars 8,496（弱信号）。
- **评价**：这是本次开源轨道中对本课题**最有决策价值的一条**：它是唯一把"现阶段不上向量库"写成**可执行判据**（触发阈值 + 非触发条件）的项目，并且**给出了零 LLM 的纯符号检索在公开基准上的实际水平**——hit@1 0.534 / hit@5 0.668。与对照基准相比有两点直接可比：其触发下限（5k–10k 页）比本项目的 22 个案例高 2–3 个数量级；其"融合后再做权威度调整"的设计，与本项目"加权打分 + 人工确认"在意图上一致（都不让相似度单独决定什么算权威）。局限：单一项目自评、无第三方复现；基准记录是其自建 harness 产出，不可直接与厂商数字比较；其 `hit@k` 口径是检索层而非端到端问答。

| 无答案/拒答能力 | 已被写进公共口径（[A-12] 的 abstention、[A-11] 的选择性遗忘），但公开报数普遍剔除该类（[A-14]、[I-07]、[O-01] 只计 470/500） | 厂商文档未把拒答作为能力项披露 | 判分规则宽松，且对抗类不可用（[O-05]、[O-06]） | **证据不足**：所有人都在口径里承认它重要，但公开数字里几乎看不到它——**这正是本项目前瞻测试 3/3 失败的那一项，且没有外部基线可对标**。 |
| 删除与合规 | 本轨道未找到"记忆存储删除权"的学术材料（检索只命中模型权重卸载类 unlearning） | 托管记忆删除与源数据解耦、传播有窗口、部分合规框架下功能整体不可用（[I-05]） | git 版本化天然提供历史与冲突解决（[O-03]） | **工业侧独有证据**。对本项目意味着：自建单副本形态在删除语义上天然更简单，这是"零托管"路线一个未被计入的合规优势。 |
| 公开基准数字能否用于选型 | 基准自身存在答案键与判分效度质疑（[A-13] 的口径不一致、[A-14] 的基线口径问题） | 同一对抗双方给出 84% → 75.14% → 58.44% 三套数字（[I-07]、[I-08]）；两厂商口径逐项不同、1.5–2.2 分差落在口径差异内（[I-04]） | 判分脚本一为确定性、一为宽松 LLM 判官，且被后续基准逐字复制（[O-05]、[O-06]、[O-08]） | **分歧**：厂商侧的数字**不能用于跨厂商选型**；我采信"口径披露完整的一方更可作为方法论参考"（[I-04]），但不采信其分数能代表我的场景。 |

- **共识（三条线互相印证）**：①关联/关系层值得保留，但形态应是稀疏、判别性、可确认的，而不是图库；②检索精度治理的重点在装配与写入元数据，而非索引替换；③记忆单元数量本身构成精度约束（[I-02] 的 200 行/25KB、[O-02] 的 2000 条、[O-01] 的 5k–10k 页），因此"规模触发重估"应当被写成可测阈值而不是感受。
- **分歧**：①**向量层必要性**——[A-05] 给出负面证据，[A-01]/[O-01]/[I-01] 给出"按需触发"的正面处理。我判定后者证据更强，理由不是数量而是**可比性**：[A-05] 的对照是在公开端点、以端到端准确率进行的，而 [A-01] 与 [O-01] 给的是检索层指标与可测阈值；两者可以同时成立——即"在 LongMemEval 级负载上纯符号检索会掉分，但在本项目规模上它不是瓶颈"。要分清这两句话，需要的是本项目自己按查询类型分层的测量，而这恰好尚缺。②**公开分数**——厂商之间的互诉说明该赛道的数字生态不可信；我倾向采信披露更完整（给出分母、模型、检索预算、延迟分位）的一方作为方法论样板（[I-04]），但拒绝任何厂商的分数作为对本项目场景的预测。
- **证据不足**：①"确定性规则抽取 vs LLM 抽取"没有任何论文做直接对比实验，粒度漂移也无人量化（学术轨道专门为此标注了材料稀薄）；②"记忆单元数量增长 → 检索精度退化"没有一篇以此为主动实验的工作（[A-10] 是最接近的，但它只给出定性判断且我未读到结果章节）；③**真实用户侧的退化报告完全缺失**——开源轨道一条 issue/PR 都没读到，所以"规模上去以后精度会不会坏"目前只有设计约束与合成实验两类证据；④被遗忘权/合规删除在学术轨道没有材料。

## 6 综合评价与观点

> 本节是我的判断，与前述来源陈述明确区分。凡是来源主张我都标了键；凡是我推断的都给出理由。

### 6.1 证据支持的结论

1. **"现阶段不必上向量库/图库"这个结论成立，但它成立的机制与项目文档目前的表述不同。** 项目文档倾向于用"入口召回 99–100%""扩展新发现 110 条"这类自评数字支撑；而外部证据支持的是一个更弱但更稳的命题：**在这个规模与工作负载下，向量层与图库的增益无法被任何一方证明，而它们的代价是可测的**——图库的代价是 ingest 与运维（[A-08]、[O-04]、[I-03]），向量层的代价是索引构建与存储膨胀（[I-03] 的 DiskANN 复盘）、以及检索被计价（[I-09]）。同时，"零向量库作为产品默认形态"有文档与代码双重先例（[I-01]、[O-03]）。
2. **关系层值得保留，但形态应当更保守。** 三份独立工作都指向同一形态：**关系只要稀疏、判别性、可确认的少数几类**（[A-02] 只有 merge / supersession / contradiction 三类且只做一跳；[A-03] 干脆是一张带 standing 标签的依赖表；[I-03] 的工业版本放弃跨图全局遍历）。这与项目第二轮"只有稀疏跨簇边通过判据、稠密簇内边噪声放大"的实测完全同向。
3. **真正被外部证据支持的"下一步投入"是写入侧，而不是检索侧。** 三条：①通用生命周期元数据（时间、来源、活跃/失效、槽位键）承载了正确率收益，细分本体只买校准（[A-07]）；②不可逆损失主要由保留/淘汰策略决定，且大部分不可由更好的检索挽回（[A-09]）；③"证据识别"与"策略执行"解耦后的增益远大于替换最后一步的算子（[A-04]）。这三条共同指向"**把字段与生命周期补对，比把打分器调好更值钱**"。
4. **精度治理必须按"检索 + 装配"两段来做，并且过滤要发生在排序之前。** 前者有量化支撑（[A-04]）；后者既是安全要求（[I-06]：过滤发生在排序之后时，被排除内容仍占据候选位，灌库攻击因此有效），也是 [O-01] 的实现选择（融合后再做权威度调整）。项目现有的"确定性加权打分 + 档位门控"在结构上已经符合这一形状，**问题只在参数（通用词泄漏），不在架构**。

### 6.2 被高估或过度声称的部分

- **厂商的基准分数不可用于选型，且这一条有完整证据链。** 同一基准、同一对手系统，公开数字依次出现 84% → 75.14% → 58.44%，每一版都伴随方法学指控（[I-07]、[I-08]）；两厂商的口径（读模型、判模型、检索预算、context 大小）逐项不同，1.5–2.2 分的差距落在口径差异量级内（[I-04]）。**任何以"某产品 LoCoMo 92.5 / LongMemEval 94.4"为依据的选型判断都是不可靠的。**
- **Mem0 论文的"26% 相对提升 / 91% 延迟降低"是最常被引用、也最容易被误读的一组数字。** 我核读全文后的具体问题：它的 OpenAI 基线**在延迟里不含记忆抽取成本**（原文明确写该成本"is not reflected in the reported metrics"），而抽取恰恰是记忆系统的主要成本项之一；同时该基线在检索侧被授予全部记忆。这两处偏差方向相反，使"相对提升"既不能作为端到端对比，也不能作为单侧劣势的修正。
- **"图记忆有价值"这一印象主要来自论文标题与厂商材料，而不是它们自己的数字。** 那篇论文自报"加图约 2%"、单跳为负增益、多跳零增益（[A-14]）；另一家厂商的图只做共现边与排序提升。把"图"当作收益来源是有文献依据的；把"图库"当作收益来源没有。
- **厂商的精度数字在时间维度上不稳定。** 同一厂商同一基准，2025 年的页面给的是"相对全上下文基线的增量"（并诚实披露某一类别下降 17.7%），当前页面给的是绝对准确率 90.2%，读/判模型从 gpt-4o 系换到 gpt-5.4——**同一产品的"能力数字"在一年内被换了口径与模型栈**（[I-04] 及其页面的时效缺口）。
- **"记忆越多越准"没有证据，反向证据反倒有一处。** 公开实现给出的体量经验上限（[I-02] 的 200 行/25KB）、厂商自己的规模告警阈值（[O-02] 的 2000 条 / top_k 50 / 2 秒）、以及流式评测的定性结论（[A-10]）都指向相反的直觉。

### 6.3 尚未证明的问题

1. **"确定性规则抽取 vs LLM 抽取"孰优，本次调研无法回答。** 学术轨道专门为此标注了材料稀薄：没有任何论文做直接对比实验，粒度漂移也无人量化；最接近的是一条负面证据（抽取阶段会丢掉承载冲突的语境/时间/来源关系，见附录 B 的 TANGLE）。**项目正在走的"确定性优先 + 语义兜底"路线，目前是设计选择而非有依据的选择。**
2. **"记忆单元数量增长 → 检索精度退化"没有一篇以此为主动实验的工作。** 最接近的是 [A-10] 的定性结论与 [O-02] 的厂商阈值。项目自测的"案例 9→22 时噪声/查询 0.25→0.91"在外部没有可对标的曲线。
3. **拒答能力没有外部基线可对标。** 它被写进公共口径（[A-12] 的 abstention、[A-11] 的选择性遗忘），却在公开报数中被系统性剔除（[A-14]、[I-07] 剔除对抗类；[O-01] 的公开记录只计 470/500 题）。这意味着**项目前瞻测试里 3/3 失败的误报问题，既不能靠对标外部数字来定位，也不能用别人的分数来安慰自己**。
4. **被遗忘权/合规删除在学术侧无材料，在工业侧只有单侧证据**（[I-05]）。删除是否真正传播到底层向量库/图库的副本与备份，**三家厂商都没有说明**（这是行业级空白，不是本次检索遗漏）。
5. **"非向量架构在真实工作负载上会掉多少分"仍未定。** 唯一明确的反向证据（[A-05]：-22.0 / -26.5 个百分点）发生在 LongMemEval 级的历史规模与公开端点上，与项目场景相差数个数量级，**它证明了"该测量"的必要性，而没有证明"该项目会掉分"**。

### 6.4 若现在必须决策，我的建议

1. **维持"零向量库、零图库"的架构判断**，并按 [O-01] 的形式把它从"立场"改写成**可测的重访触发条件**（建议直接采用其形状：规模阈值、p95 延迟阈值、以及"向量相比现有通道带来 +5–10% recall@5"这类效果阈值），写进 `FRAMEWORK_READINESS.md` 的重访清单。
2. **把 `PENDING.md` §2 的"通用词泄漏：保留不修"改判为"先修，且作为独立回归项"。** 理由是外部证据把精度治理的地位抬高了（[A-04]、[I-06]），而且项目自己的前瞻测试显示它是**唯一已被证实的误报根因**（NOVEL 3/3）。修法建议优先"跨通道去重"与"多组件键要求 ≥2 个组件命中"两条，因为它们在结构上等同于 [I-06] 的"先过滤后排序"。
3. **把下一个迭代的主要工程量投到写入侧元数据**，按 [A-07] 的消融结论排序：先补**通用生命周期字段**（告警事件时间与案例入库时间分开存、来源、活跃/失效标志、槽位键），再考虑细分类型（细分类只买校准）；这一步同时兑现 [A-09] 的不可逆损失与 [I-06] 的溯源要求。
4. **把"补测 3：查询形态测试"按查询类型分层重做**，而不是做一次整体自然语言召回测试（依据 [A-01]：同一底座在不同负载上一个通道可以完全不必要、在另一个负载上不可或缺）。
5. **补一项"拒答"验收测试**：库外内容必须静默，且要以"硬负例 + 误报率"的形式写进指标（参考 [A-12] 的 abstention 与 [I-06] 的先过滤后排序）。当前 3/3 强档误报在外部证据里属于**已被识别为结构性盲区**的失败模式（[A-06]），不是可以靠调阈值消掉的瑕疵。
6. **图的问题按项目自己的路线图走，不必再等外部证据。** [A-02]/[A-03]/[I-03] 已给出足够清晰的形态约束（稀疏三类关系 + 一跳 + 人工确认 + 不建全图 + 不做跨图遍历），足以支撑"条件采纳 B"落笔；剩余的不确定性在实现细节，不在方向。

### 6.5 建议继续跟踪的方向

- **装配/读取环节的公开标尺**（[A-04] 所属切片的多跳公共天花板 ≤7%）是否会随新工作被打破——它直接决定"关系层能不能带来多跳收益"这个问题什么时候才有外部答案。
- **工作负载自适应的检索路由**（[A-01] 类）是否会成为主流形态；若是，则"向量层的取舍"最终会被一个每查询决策的级联路由取代，而不是被一次架构选择决定。
- **记忆投毒的防御有效性度量**：目前只有攻击侧数字（[A-06] 的效用曲线）与厂商的定性控制清单（[I-06]），**没有防御侧的可比较结果**（无 ASR 对照、无误报率）。这是本项目若要上关键生产环境必须自己补的一类证据。
- **"删除是否传播到底层副本"是否会有厂商给出明确说明**（当前三家都没有，[I-05]）。它决定托管记忆能否进入受监管场景。

## 7 局限

1. **检索截止 2026-09-28**，此后发布的结果未纳入。本领域迭代极快（[I-04] 的模型栈在一年内即被更换），故本文的时效性衰减会比一般课题更快。
2. **渠道限制，且影响到具体结论**：本机 `github.com`、`raw.githubusercontent.com`、`cdn.jsdelivr.net`、`dl.acm.org`、`huggingface.co`、`api.openai.com` 均不可达；shell 的 `curl`/`git` 因 TLS 与连接受限不可用，全部取数经 `node fetch` 与桥接通道完成。后果有三：**开源轨道没有任何本地克隆，全部仓库证据经 `api.github.com` 获取，没有一条经过构建或运行**；**ACM/Elsevier 正文基本无法获取**，非 arXiv 且无预印本版的同行评审来源可能存在系统性缺口；`web_search` 有 5 次因上游限流失败，学术轨道的发现主要依赖 arXiv API。
3. **部分条目只读到摘要或前半**：学术轨道中 [A-08] 我只读到摘要与元数据（结果表未核）、[A-10] 只读到设计与方法章、[A-02] 的 66.6% 与"最高"的基线集合未核、[A-07] 的实验章未核（其数字来自摘要与引言）；这些条目内的数字均已注明来源层级。工业轨道中 [I-01]/[I-02]/[I-03]/[I-04]/[I-05] 等多条页面**无绝对日期**，无法支撑精确时效判断（已逐条标注）。开源轨道中 [O-05]/[O-06] 的许可未确认，多条未取 commit 哈希。**我亲自复核了承重的四条**（[A-14] 全文、[O-01] 的向量后端策略与基准记录、[O-02] 的融合公式与规模常量、[O-05] 的判分脚本），其余条目依赖子代理账本 + 我对其原文的抽读；**凡我未亲自打开的一手页面，其数字一律标注为"来源自陈"。**

## 附录 B 未纳入但值得注意

以下条目在读到时被评为相关性边缘、置信度偏低、或与已选结果重复，故未进入 30 条正文（**已读到的内容与访问深度记录在 `evidence/` 下的三份子代理账本中**）。

- **TANGLE**（arXiv:2608.13921）：541 例"真正无法消解"的记忆冲突基准，明确把"抽取阶段丢掉承载冲突的语境/时间/来源关系"指为上游瓶颈——与本项目"人工确认边"的设计直接相关，因摘要无任何数字而未纳入。
- **Selection Integrity for LLM Graph Memory**（arXiv:2606.12290）：论证一旦关系边可由非信任来源自动写入，"选择"本身成为攻击面，且基于记录来源的防御按构造失明（被引用的证据全部干净）。**这是"人工确认 vs 全自动建边"在安全侧的量化理由**，因我未读到其判定与实验章节而列为旁证。
- **PMPA**（arXiv:2609.13889）与 **MPBench**（arXiv:2606.04329）：经记忆持久化的注入在真实 harness 上的成功率（OpenClaw 73.7%、Claude Code 66.9%；跨会话 55.5% / 81.7%）与"四条写入通道 / 九类结构性脆弱点"的分类法。与 [A-06]、[I-10] 同向，未纳入以控制条数。
- **EnSIMem**（arXiv:2609.27279）：`[实体][类型][属性:值] → episode_id` 索引 + 原文保留，并把"属性粒度"提为核心折衷——与本项目正在讨论的"动作/实体粒度"问题几乎同一命题；因摘要无数字、实验章未读而未纳入。
- **两份综述**：arXiv:2602.06052《A Survey of Agent Memory in the Second Half》（三维视角：记忆基质 / 认知机制 / 记忆主体，明确把领域定位为"从跑分转向严格真实世界评测"）与 arXiv:2605.06716《From Storage to Experience》（存储 → 反思 → 经验三阶段）。综述不产生新证据，仅作分类坐标。
- **LongMemEval-V2**（arXiv:2605.12493）：451 题、轨迹最多 500 条 / 115M tokens，最佳方法为"把轨迹存文件 + 调用编码 agent 取证"（72.5%，优于最强 RAG 基线 48.5%），代价是高延迟。它代表 2026 年的前沿方向（agentic retrieval），与本项目的符号检索是可组合关系而非替代关系。
- **记忆投毒一族**（arXiv:2601.05504、2603.20357、2609.00523 等）：本次经 arXiv API 检出多篇 2026 年工作，未逐篇阅读，故不描述其结论。
