## 可能问题：

P1（高）LCS「一步一观测」把同一 step 的其它证据行整条吞掉

官方样本每 incident 8 行，输出只剩 6 行：S1 只报 WEB0410002（WAF0410001 消失）、S3 只报 WEB0410005（RASP0410004 消失），且选中的是时间较晚那条而非最早那条 → 证据归属不稳，跨源同请求（waf+web 双看，正是原链层信号 2.5 的原料）在输出里也看不出来了。
更糟的形状：批内 S6(DNS) 行在前、S1..S3 在后 → 证据只报 S1..S3，而 unobserved_steps 里写着 S6，那条 DNS 行在输出中完全不出现（不在 evidence / gap / mismatch）。
混批回归：12 行 = 两起攻击（host app-a / app-b）、无 incident_id → 落成 1 个 unassigned batch scope，输出 complete 6/6 (strong)，6 条证据全取自第二起攻击，第一起 6 行全部消失（因为 complete，前后段/缺口都是空）。也就是说：incident 分区只对已标注 incident_id 的行生效，新批（ingest 不写 incident_id）照样混，而 LCS 让混批痕迹从"多出的证据行"退化成"完全看不见"。
建议：形态/tier 继续用 LCS，但 evidence 恢复成"该 step 的全部来源符合命中行（按时间排序）"，另开一个 dropped/out-of-order 桶；unobserved_steps 只算"该动作零观测"的位置。

P2（中高）同名 action_id 的正则不校验，检测取并集 → 跨案例假阳性 实测：造一个 CASE-030，只留 S1、action_regex 改成只匹配 /ecp/ZZZONLY/。build_action_index 把两条正则并集成 exch_proxylogon_ssrf 的 rules，喂一条 /ecp/7b37f0/ 的真样本行 → CASE-030 报 complete 1/1 (strong)，证据正是它自己正则匹配不上的那行。你给 generic 做了跨 pattern 一致性保护，regex 却没有对称保护，且对齐只用 action_id、不复核本步正则。建议：对同 action_id 的不同 regex 直接报错（与 generic 对称），或检测按各 pattern 自己的规则集；顺带说，索引里的 refs 已经能做原方法的"分叉参考"，目前没有输出口。

P3（中）标签与「最新决策」会打架 实测：confirmed 之后再追加一条同 event/step 的 candidate → 标签仍是 case_id=CASE-029/incident_id=INC-LAB-E，而关系表最新一行是 candidate。文档写"latest link = current status"，但标签只在 confirmed/rejected 时变更，降级（candidate/fixture）不回滚；而 lookup_case_logs 是按标签查的，会把已降级的行当既定事实输出。建议按关系表最新状态重算标签，或 lookup 时 join 关系表显示状态。

P4（中）lookup_case_logs.py 把合成 fixture 当 CASE-029 的历史观测输出 --case-id CASE-029 → "16 stored observation(s)"，其中 8 行是 INC-DEMO-CASE029-001（SYNWAF0511001… 合成 fixture）；输出不带 event_id、不带 link_status、没有任何 fixture 标记，而 pattern 的 provenance.observation_count = 1。这与文档"fixture must not be presented as a real observation"直接冲突。建议：join event_pattern_links.csv 打印状态，默认排除 fixture（或加 --include-fixtures）。

P5（中低）标签回写会整文件重写证据文件，并丢列/规整换行 实测：把 raw_logs.csv 改成 LF 并加一列 note（值 keepme），跑一次 confirmed link → 全文件变 CRLF，note 列及其值全部消失（按 RAW_FIELDS 重写 + extrasaction="ignore"）；BOM 与时间戳/来源/内容确实未变。另外「先 append 关系行、再写标签」两步不原子，中间失败会留下"关系表已记、标签没写"。建议：只改受影响行（或保留未知列/不支持就报错），并把两步顺序/原子性说明清楚。

P6（低） 全步骤都标 generic 的 pattern 永远拿不到 strong（matched_non_generic=0），原方法的 1/1 单动作案例（DGA 类）是"完整=强"。文档已按新口径写，但建议 add-pattern 直接拦住"所有步骤都是 generic"的 pattern，而不是静默降档。

P7（低，健壮性） CSV 行短于表头时 content 为 None → extract_log_actions 直接 TypeError 崩栈（我故意构造畸形 CSV 时撞到）；读入侧没有 ingest 那样的列校验。另外"动作命中但来源不符"会显示 shape=none 0/6 (weak)，配着 mismatch 数读起来别扭（原方法是给该位置标 ◐）。
