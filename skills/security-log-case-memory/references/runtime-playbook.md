# 运行手册（每批日志：检索 → 判定 → 提取）

配套 `SKILL.md`（常读版）使用：本文件是「真正分析一批日志时」的展开细节。**开发/升级/加层/回归不走这里**，走 `references/upgrade-playbook.md`。
所有命令在 `F:\AI_Learning\AgentMemory` 根目录执行；检索器 = `src/retrieve.py`（v2 动作匹配 + v2.1 链层）。

## 0. 一批日志的固定顺序

| # | 动作 | 命令 / 做法 | 产出 |
|---|---|---|---|
| 1 | 落盘 | 逐行写 `data/incoming_logs.txt`（`ts [source] log_id content`，保留截断原样） | 批次文件 |
| 2 | 行级分诊 | `python src/retrieve.py --batch data/incoming_logs.txt` | 每行候选 + 档位 + 形态（提示级） |
| 3 | 链级判定 | `python src/retrieve.py --chain data/incoming_logs.txt` | 候选链 + 链级匹配（判定级） |
| 4 | 判定 | 对照 §2 决策表，逐链给结论 | `[检索: CASE-xxx]` / 【新案例】/ 无关 |
| 5 | 提取 | 读 `references/case-write-spec.md` → 五处写入 → `python scripts/derive_action_sources.py` → `python scripts/build_action_index.py` | 库更新 |
| 6 | 验证 | `python eval/run_action_recall.py` + `python tests/test_chain_assembly.py` + `python tests/test_chain_integration.py`（动过库/脚本/代码才跑） | 数字不变 |

> 生产批次若要接结构化日志（`log-schema/`），先读 `references/production-log-schema.md`（适配层尚未实装）。

## 1. 检索输出怎么读

### 1.1 行级（`--batch`，分诊）

- **候选数量**：动作通道命中**全部列出**（无上限）；只关键词命中的进「关键词兜底」区单独列出；每条候选附最多 3 个**分叉参考**（这一行同时还命中哪几条案例）。
- **档位**（置信度，不是分数）：`完整` = **强** · 其余形态且 `命中≥2` = **中** · `命中=1` = **弱**（通用探针 generic 单发尤其按噪声）。
- **形态**：完整（连续 + 起于 0 + 到末位）/ 前缀（连续 + 起于 0）/ 中段（连续但不起于 0）/ 缺口（不连续，会列出「缺口(未观察): …」）；每条还带「前段未观察: …」与「预测下一步: …」。**缺失/跳步不扣分**，只是拿不到强档（`完整` 是唯一通向强档的形态）。
- **排序键**：档位 → 命中数 → 关键词分 → 覆盖度 → 案例号。
- **关键词兜底区**：`≥6 强 / 4–5 中 / ≤3 弱`（弱=噪声）；权重 `keys×3 / mitre×2 / ind×2 / sig×1 / probes×4`，跨字段 token 去重已生效。
- 已知歧义行：911-920-3-3（F5 rasp 截断行）= CASE-010 第 1、CASE-011 第 2 → **接受现状，勿调分**。

### 1.2 链级（`--chain`，判定）

- **前置**：批内组装候选链（信号：会话 ID > 实体共享 > 同请求跨源并发（Δt≤30s + 共享动作或同 URI 路径 + 至少一侧非通用动作）> 载荷模板；阶段回退≥2 档且实体不同 → 切链）。组装只做**候选生成**，链归属由 Agent 确认（可拆可并）；**跨批次不串链**。
- **符号**：`●` 命中 · `◐` 来源不符（该阶段观测层 ≠ 案例该阶段期望来源 → **不计入匹配计数**，并连带降形态/档位）· `○` 未观察 · `⚑` 低置信拼接/顺序异常（待确认）· `⚠ 链未闭合` = 攻击进行中。
- **顺序一致性**：链内时间序与案例序列相反 → **降一档** 并提示「顺序异常」。
- **显示条数**：算法算出全部候选并按同构键排序，`show_chain` 默认**只打印前 3 条**（要全量可临时调 `top_n`）。
- 行级结果会并列附在链输出里（分诊用途）。

## 2. 判定决策表（信号 → 含义 → 动作）

| 检索输出 | 含义 | 你的动作 |
|---|---|---|
| 完整（强） | 链闭合、与案例吻合 | 判 `[检索: CASE-xxx]`；按案例链序复述攻击叙事 + 处置要点 |
| 前缀 / 中段（未闭合） | 攻击**进行中** | 按「预测下一步[预期来源]」主动等/拉取该源证据；事件按「进行中」升级，别急着收尾 |
| 缺口 | 案例期望的中间步骤没看到 | 两种解释：该源未采集 / 攻击者换手法 → **定点核查该阶段**（缺口=webshell 落地 → 去 web/rasp 找落地证据） |
| 弱档（含通用探针单发） | 通行探针、噪声 | 不作判定依据；结论里注一句「分诊提示: …」即可 |
| 关键词兜底强分（动作通道空） | 词面像、行为不像 | 不判案例；标【疑似/待观察】，并考虑动作库是否漏了该形态 |
| `◐ 来源不符` | 动作对、观测层不对 | 疑似**另一台机器/另一次攻击** → 不并入本案，单独成链看 |
| `⚑ 低置信拼接/顺序异常` | 组装可疑 | 先人工拆/并链，再判定 |
| 候选为空 | 技术不在库中 | **【新链案例】** → 走提取流程（`case-write-spec.md`） |
| 多候选并列 | 分叉（同技术不同链） | 按「档位→命中数→关键词分」取主判，结论里写明次选与分叉理由 |

## 3. 判定纪律（五条）

1. **链级 = 最终判定单元**，行级只是分诊；两者冲突时以链级为准并写出理由（例：9101-9110 首个链，CASE-016 中段 2/4 中档胜过 CASE-003 的 1/4 弱档）。
2. **弱档 / 通用探针单发 = 噪声**，不作判定依据。
3. **关键词兜底强分 ≠ 匹配**（动作通道主区永远压过兜底区）。
4. **`◐` / `⚑` 的处理**：`◐` 不计入匹配计数、不并入本案；`⚑` 先拆并再判。
5. **候选为空 → 新建案例**，不要硬套「最相近」的案例；多候选要写清分叉。

## 4. 提取入口与判据

- 写案例：`references/case-write-spec.md`（**五处写入 + 顺序**：① 案例本体 → ② `ACTIONS` → ③ `STAGES` → ④ `SEQUENCES` → ⑤ `BATCH_EVIDENCE` 登记 → `derive` → `build`）。
- 合并 vs 新建：同路径/同指纹/同工具链 → **合并强化**（追加 targets/domains/IPs、观测次数、差异标注）；同链不完整观测（前缀）→ 并入原案例；技术不同（哪怕同家族）、后续动作不同（分叉）→ **新建**。
- 证据从严：只写日志可见内容（如「仅见 LFI 阶段，无后续载荷证据」），不夸大。
- **批次留档（重要）**：判定为入库后，把该批复制到 `data/batches/<批次日期>_<主题>.txt`，并在 `BATCH_EVIDENCE` 里登记**该副本路径**——`data/incoming_logs.txt` 会被下一批覆盖，直接指它会让已入库案例的来源证据失效（详见 `data/batches/README.md`）。

## 5. 边界与常见误用

- **候选 ≠ 判定**：一条噪声探针也会产生候选，「召回列表」不等于结论；行级候选多 ≠ 多次攻击（链级才是「一次攻击」的粒度）。
- **回顾性 vs 前瞻性**：新增案例后重跑检索是回顾性审计（证明可召回），不得当作事前检出；`dataset/data-921-930.txt` 保持未入库作前瞻批。
- **链级数字口径**（勿混用）：组装 35/35 正确并链 · 0 碎片 · 0 误并；链级 Top-1 57/58（1 条例外 = 9101-9110 混合载荷链，已记录并注明理由）；行级 123 特征行 · Top-1 122 · 动作命中 123 · 强档 60。
- 同源模板重叠只在 300s 内并链（`TEMPLATE_SAME_SRC_S`）；碎片化/误并优先调 `src/chain_assembly.py` 顶部旋钮，**不要改行级打分**。
- 不要为「字段重叠/重复」删关键词字段（实测边际价值：关键词通道整体 3 行兜底排序、动作通道 0 变化）。
- 时序/节奏类结论：统一计时锚点、标「观察级」、n=1 标「待验证」、注明来源覆盖限制。
- **批次来源先核对**：拿到一批日志先按 `log_id` 搜 `dataset/parsed_*.json` + `dataset/*.txt`（精确匹配全量搜，别用被 `head` 截断的 grep 输出下结论）——它可能就是某个已标注单元的复现/变体，此时应比对「该单元的人工期望」而不是当成新形态。**若批次来自前瞻批（如 921-930）**，它的期望在 `history/old_eval/run_recall_unseen.py`。
- **新增动作的门禁必须同时覆盖「样板行 + 前瞻 NOVEL 行」**：除本批证据行外，还要在 dataset 三文件的通用样板行与 921-930 NOVEL 行上零命中（否则会破坏「样板行零动作误命中 / NOVEL 零中强档」两条铁律）。已实测反例：HIDS 进程链格式（`cat /etc/passwd … <== /bin/sh -c … <== <父进程名>`、`/bin/(dash|sh|bash) -c`）在库外就有 **10 条同格式样板行**（连 `app-server` 父进程那一版都在 911-920 里），按门禁**不可作动作**；干净的只有 `rememberme=` 这类载体（0 特征行 / 0 样板行 / 0 NOVEL）。
- **弱档模板再现 ≠ 新案例**：当一批行只共享一个通用探针（如 `cmd=127.0.0.1;id`）、且其判别性后续阶段全未出现时，若该探针正是某案例（如 CASE-010/011）的入口动作，应判「弱档模板再现 / 待观察」，而不是因“候选链未闭合”就建新案例；配套证据：单独出现的主机进程链样板行不构成新证据。
- **已知边界（不放宽）**：同秒 / 同 URI / 同参数的三层观测，若唯一共享动作是 generic，组装**不会**并链（抗粘连优先）→ 链归属由 Agent 人工确认；实证与盲测对照见 `eval/results/report_unseen_unit10_blind_test.md`。
- 勿混淆机制：真实 Hermes 记忆 = `MEMORY.md`/`USER.md`（2200/1375 字符、会话全量注入、无检索）；本验证 = JSON 案例库 + 检索协议。
