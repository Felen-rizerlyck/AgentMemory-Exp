> 本文件是当前**最新版方法流程指南**。旧版（关键词双通道打分，v1）已归档至 `history/`（`old_` 前缀），保留可运行作对照，不再作为现行方法。

## 一、机制总览

**核心设想**：每个攻击以**形式化的动作链**存储（攻击链阶段序列细化为"去变量的动作指令"），检索时以**动作序列匹配为主 + 关键词匹配为辅**。

| 通道 | 角色 | 内容 |
|---|---|---|
| **动作通道**（主，v2 新增） | 结构化匹配 | 动作库正则识别日志行中的动作 → 反向索引取候选案例 → 案例动作序列位置对齐 → 完整/前缀/中段/缺口四类匹配 + **下一步动作预测** + **分叉相似案例** |
| **关键词通道**（辅，v1 保留） | 兜底 + 并列排序 | `retrieval_keys`(×3) / `mitre`(×2) / `indicators`(×2) / `signature`(×1) + `pattern_probes`(×4)，跨通道去重，与 v1 同口径 |

关键设计（源自可行性分析结论）：

1. **动作 = 去变量的指令/行为模板**：`wmic /node:<ip> process call create`、`ssh -i <keyfile>`、`DGA 随机子域查询`。变量（IP、文件名、域名）不参与匹配，基础设施更名后仍可召回（如 DGA 换域）。
2. **案例仍为完整单元，以动作为索引**：案例不拆散，`action_sequence` 按攻击链顺序引用动作库中的动作 id。检索时现建反向索引（动作 → 案例），零外部依赖。
3. **停止条件 = 最长可观察重合**：不再"匹配到最短重合就停"，而是返回命中路径上的所有案例 + 标注匹配深度，前缀案例不被完整案例遮蔽，未观察的下一步动作变成**预测**。
4. **单行日志 = 单链片段**：一条日志行通常只暴露攻击链的一段（WAF 行见入口、HIDS 行见主机侧），动作对齐天然表达"链中段/缺口"视角，不要求每行完整命中。

## 二、记忆结构（`data/memory_store.json`）

```jsonc
{
  "cases": [ /* 案例实例，schema 见下 */ ],
  "action_library": { /* 动作 id -> {label, regex, generic} */ },
  "activity_patterns": [ /* 跨案例活动模式【实验性子层】，观察级置信度 */ ]
}
```

**案例字段**（在 v1 schema 上新增 1 项）：

| 字段 | 说明 |
|---|---|
| `id` / `source` / `attack_type` / `kill_chain` / `mitre` / `indicators` / `signature` / `reasoning` | 与 v1 相同 |
| `retrieval_keys` / `pattern_probes` | 与 v1 相同，供**关键词通道**使用 |
| `action_sequence` | **v2 新增**：按攻击链顺序的动作 id 列表 |

**动作库条目**：`action_id -> {"label": 去变量后的动作名, "regex": 结构正则, "generic": 是否通用探针}`

- 共享动作（`cmd=id` 探针、`echo;id`、`java 序列化魔数 rO0AB` 等）跨案例复用——复用本身即案例间相似性的来源（分叉参考）。
- `generic=true` 标记通用探针（whoami / cmd=id / echo;id / id;hostname 等），单发命中仅作弱参照，不单独支撑结论。判别性由**序列位置**提供，不由单动作提供。

## 三、检索协议（每批日志标准流程第一步）

```bash
# 单条检索
python src/retrieve.py "ssh -i /tmp/.key -o StrictHostKeyChecking=no root@10.20.8.183 \"id; hostname\""

# 批量检索（逐行）
python src/retrieve.py --batch data/incoming_logs.txt
```

### 动作通道匹配形态（对齐算法）

对一条日志行：① 动作库正则识别出现的动作（按行内位置排序）；② 反向索引取候选案例；③ 每个候选案例做**位置对齐**——观察到的动作落在案例序列的哪些位置：

| 形态 | 定义 | 档位 | 附加输出 |
|---|---|---|---|
| **完整匹配** | 序列所有位置连续全命中（n/n） | 强 | — |
| **前缀匹配** | 从链头连续命中，未到链尾 | 中（命中≥2）/ 弱（命中 1） | **预测下一步**：链上未观察的第一个动作 |
| **中段匹配** | 连续命中但未含链头 | 同上 | 前段未观察动作列表 + 预测下一步 |
| **缺口匹配** | 命中位置不连续 | 同上 | 缺口（未观察的中间动作）列表 |

- **分叉参考**：命中案例之外，与本次观察共享动作的其他案例（= Trie 中被剪掉的分叉分支），列于命中项下，不并入结论。
- 排序键：档位 → 命中数 → 关键词分 → 覆盖度 → 案例号。

### 判读规则

- 动作通道：完整 = 强档（含 1/1 单动作案例，如 DGA）；命中 ≥2 = 中档；命中 1 = 弱参照（按噪声处理，尤其 `generic` 动作）。
- 关键词通道兜底：强 ≥6 / 中 4–5 / 弱 ≤3（弱按噪声处理）。
- 无动作命中且无实质关键词命中 → 【新案例】。
- 分析结论对检索支撑显式标注 `[检索: CASE-xxx]`，无实质命中标【新案例】。

### 输出示例

```
== 查询: wmic /node:10.20.6.179 process call create "cmd.exe /c whoami"
   [动作] 识别: WMIC 远程进程创建 (wmic /node:<ip>) → whoami 侦察探针
   [动作] [CASE-001] 前缀匹配 2/4（中）横向移动 / 远程命令执行 (WMIC)（载荷演进：侦察 → 持久化）
        - 链: ●1.WMIC 远程进程创建  ●2.whoami 侦察探针  ○3.创建后门账户  ○4.账户加入本地组；预测下一步: 创建后门账户 (net user /add)
        - 关键词: score=17(强) keys×3: wmic,whoami,process call create; probe×4: wmic\s+/node:
```

## 四、提取流程（每批日志：先检索 → 再判断 → 后提取）

沿用 v1 纪律，新增动作标注环节：

1. **落盘**：日志原文逐行写入 `data/incoming_logs.txt`。
2. **检索**：`python src/retrieve.py --batch data/incoming_logs.txt`，判读见 §三。
3. **判断**：日志按独立事件处理，不跨批次串链。
4. **提取**：
   - 高度相似 → 合并强化（同路径/同指纹/同工具链；同模版再现并入原案例为观测条目）；
   - 技术不同 → 新建案例（即使同家族/共享探针模板）。前缀案例（同链不完整观测）→ 合并；后续动作不同 → 分叉共存（新案例）。
   - **新案例/新观测必须同步更新动作**：新动作入 `action_library`，案例 `action_sequence` 按链序排布；执行 `python scripts/build_action_index.py` 重新注入并校验（幂等）。
5. **动作入库门禁**（沿用 probe 判别性红线）：
   - 动作正则只锚定特有结构（技术指纹/编码形态/完整路径模板），禁止通用命令与通用路径（`;id`、`/etc/passwd`、`/bin/sh`）单独作动作；
   - 正向：命中该案例所有已知观测行；反向：不命中负样本与样板行；改后跑 `python eval/run_action_recall.py` 回归。
6. **证据从严**：只记录日志可见内容，不夸大（如"仅见 LFI 阶段，无后续载荷证据"）。

## 六、已知边界（诚实标注）

1. **严格顺序假设**：`action_sequence` 为严格先后；真实攻击中侦察/发现可能交错，届时升级为子序列/序列对齐匹配。
2. **单行单片段假设**：每行只做一次动作识别+对齐；跨行时序关联（同批多条日志串成完整链）当前不做，仍属 `activity_patterns` 实验层职责。
3. **分叉建模近似**：案例内多写法（如 CASE-021 的 sed/echo 两写法）以线性序列近似表达，检索时以"中段匹配+前段未观察"呈现；Trie 真分叉（独立案例）由提取准则保证。
4. **动作库覆盖率**：动作库由案例证据归纳，库外动作无法识别——NOVEL 行依赖关键词通道兜底（弱档）与人工判断，这正是"前瞻测试"的检验对象。
