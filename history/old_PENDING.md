## 2. 通用词泄漏（组件兜底缺陷）——已收口（2026-09-29）

> **进展**：#4 跨通道去重（2026-09-24）+ #2 结构化组件 + B2 字段设计（2026-09-29）已全部合入。回归：NOVEL 3 行**全部静默**、KNOWN 21/21、全量召回 Top-1 122/123 · Top-3 123/123 · 强档 123/123 保持、负样本零扩展、C2 自检 0 差异。
> **残留（无害）**：sig 通道的通用路径（如 CASE-003 signature 内 `/etc/passwd`）仍可能产生 1 分弱档命中，按判读规则（弱档=噪声）不计入结论。B1 停用表兜底暂缓，观察后续批次再定。

- **症状**：`key_hits` 的组件兜底把多词键/文本拆成 ≥6 字符单词逐一匹配，通用词会泄漏出分。
- **实例**：
  - CASE-001 在纯 LFI 行（Q-A-03）得 **6 分强档**：key `"process call create"` 拆出 `"process"` 命中 JS 载荷 `return process`()（keys×3+ind×2+sig×1）。
  - CASE-007 在 Zerologon 负样本得 1 分（signature 里的 `"Windows"` 命中）。
  - （新批次补充）样板 HIDS 行（`cat /etc/passwd … <== …`）：CASE-010 经 ind/sig 中通用路径（`/etc/passwd`、`/bin/sh`、`/opt/app/main`）得 5–7 分（最高样例 911-920-2-4，达强档）；CASE-017 经 key `server[REQUEST_METHOD]` 组件拆出 `server` 命中 `app-server` 得 5 分——落 4–7 分带。
  - （前瞻测试补充，data-921-930）**通用 token 的多通道重复累计**：同一单词/字段名同时命中 keys(3)+ind(2)+sig(1) 即达 6 分强档——`select`→CASE-015=6、`cmd_inject`→CASE-014=6、`process`→CASE-001=6、`deserialization`→CASE-012=6、`base64`→CASE-019=6、`username`+`password`→CASE-015=6；并扰动 C1 排序（CASE-012 超 CASE-006）。
- **影响量化**：12 条原样行中 1 条强档误命中；首轮扩展噪声 5 条中 4 条源于该假种子。
- **候选修法**（均未实施）：
  1. 多组件键要求 **≥2 个组件命中**；
  2. 组件需含非字母字符（结构化片段）才参与匹配；
  3. 维护通用词停用表（process / windows / create / execute…）；
  4. **跨通道去重**：同一 token 在 keys/ind/sig 间重复出现只按最高权重计一次（前瞻测试证据支持：可同时抑制强档误报与排序扰动）。
- **纪律**：任何修法先跑 `python eval/run_eval.py` + 历史行回归，前后对照评审。
