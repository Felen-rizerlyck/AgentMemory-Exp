# 案例记忆规模管理方案

> 日期：2026-09-29 · 状态：**分析稿，未实施** · 触发：用户在确认"向量库用不到"后，提出"案例过多导致文件膨胀/检索变慢，以及删除老旧记忆是否误判"的疑问
> 关联：`FRAMEWORK_READINESS.md` §⑥（规模扩展行为：本文把"未验证的观察项"落成"明确的对策"）· `EXTRACTION_CRITERIA.md`（提取准则）

## 一、问题：三个规模瓶颈，要分开看

当前方案（JSON 案例库 + 符号双通道检索，无向量、无图）在规模上有三个独立瓶颈：

| 瓶颈 | 机制 | 阈值估计 |
|---|---|---|
| **文件大小膨胀** | 主因不是"案例多"，而是**单案例 `reasoning`/`signature` 无限追加观测文本**（合并强化逐次追加） | 案例数增长有界（攻击手法有限、同类合并）；观测记录增长无上界 |
| **检索效率退化** | `retrieve.py` 是 **O(N) 全量遍历**，每个案例做双通道正则匹配，无索引 | 22 案例毫秒级；几百案例无感；几千案例开始明显变慢 |
| **噪声随规模增长** | 案例越多，弱档交叉命中越多，检索"脏"得越快 | 实测：9→22 案例时噪声/查询 0.25→0.91 |

## 二、四个对策（按性价比排序，都不是"删除"）

| 对策 | 治什么 | 原理 |
|---|---|---|
| **1. 倒排索引** | 检索 O(N) | 预建 token→案例映射，检索时只对"命中 token 的候选案例"完整打分，O(N)→O(候选数) |
| **2. 观测记录聚合** | 文件膨胀 | `reasoning` 里"逐次观测"压成聚合统计（"已 11 次观测，域池轮换"），不再逐次追加完整描述 |
| **3. 判别性字段与审计文本分离** | 文件膨胀 + 检索纯度 | `retrieval_keys`/`pattern_probes`/`mitre`（检索用，精简且不老化）留在主库；逐次观测流水账（审计用）归档到独立文件 |
| **4. 冷热归档** | 规模整体 | 活跃案例（近期复现）在热库，沉寂案例移冷库；检索先热后冷，冷库兜底 |

其中 2 和 3 是同一件事的两面：**检索需要的"判别性知识"很小且不老化，会膨胀的是"观测流水账"，两者本就该分开存储。**

## 三、核心原则：不删除，只合并 / 压缩 / 归档

**关键洞察：攻击手法没有保质期。** 2020 年的 WebLogic ShellSession 利用，2026 年遇到同类攻击照样该匹配——旧案例的判别性特征（`com.tangosol.coherence`、`pattern_probes` 等）**不会因"老旧"而失去参考价值**。

因此：

- ❌ **定期删除老旧记忆 = 错误策略**，会直接造成"旧手法变体因参考案例被删而被误判为【新案例】"。
- ✅ **正确替代**（三者都不丢知识）：
  - **合并**：同源案例合并（已是现有提取准则），知识聚合；
  - **压缩**：压缩"观测流水账"，判别性特征**永久保留**；
  - **归档**：沉寂案例进冷库**保留可查**，只是不参与常规检索。

一句话：**要压缩/归档的是"观测日志"，不是"判别性知识"；后者该永久存在。**

## 四、与复杂日志的关系

真实日志的判别性远低于合成数据（干净指纹/双层告警不可得），会带来：

1. **更多案例**：一条日志拆出多个动作，动作组合更多 → 案例数涨得快；
2. **更多噪声**：真实噪声多，符号匹配精度下降；
3. 这指向之前讨论的**实体-关系图**方向（`ENTITY_VS_CASE_GRAPH.md` 等）——复杂日志下案例级匹配可能不够，需动作级索引。

规模管理是**案例级记忆内部的**优化；实体-关系图是**架构级的**演进，两者不互斥。

## 五、上生产前的必做清单

| 项 | 性质 | 触发 |
|---|---|---|
| 倒排索引 | **必做** | 案例数接近几百时 |
| 观测记录聚合 + 判别性/审计分离 | **必做** | 单案例观测次数持续增长时（当前 CASE-002 已 11 次，已见趋势） |
| 冷热归档 | 建议 | 案例数 >50 且出现长期沉寂案例时 |
| 向量 advisory 通道 | 未定 | 仅当自然语言/模糊查询掉分时（见 `FRAMEWORK_READINESS.md` 补测 3） |

> 结论：当前这一版**短期（几百案例内）直接使用没问题**；规模问题的解法就是 §二 四件，其中"倒排索引 + 观测聚合/分离"是上生产前必做的两件，且都不涉及"删除记忆"，不会引入误判风险。
